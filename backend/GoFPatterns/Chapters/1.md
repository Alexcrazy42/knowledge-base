# 1 глава. Введение в паттерны проектирования

В этой книге под паттернами проектирования понимается описание взаимодействия объектов и классов, адаптированных для решения общей задачи проектирования в конкретном контексте.

В паттерн MVC входят сразу же несколько паттернов: наблюдатель, компоновщик, стратегия, фабричный метод и декоратор.

Два критерия: цель и уровень

Цели паттернов:
1. Порождающие - контроль создания объектов
2. Структурные - композиция объектов и классов
3. Поведенческие - характеризуют то, как классы или объекты взаимодействуют

Уровень: к чему применяется паттерн, к классу или объекту

Сравнение структур времени выполнения и времени компиляции.






Агрегирование и осведомленность.
Аггрегирование подразумевает, что один объект владеет другим или несет за него ответственность. В общем случае мы говорим, что объект содержит другой
объект или является его частью. Агрегирование означает, что агрегат и его составление имеют одинаковое время жизни.

Говоря же об осведомленности, мы имеем в виду, что объекту известно
о другом объекте. Иногда осведомленность называют ассоциацией или отношением «использует». Осведомленные объекты могут запрашивать друг
у друга операции, но они не несут никакой ответственности друг за друга.
Осведомленность — это более слабое отношение, чем агрегирование; оно
предполагает гораздо менее тесную связь между объектами.


Агрегирование — это частный случай композиции, где один класс (Контейнер) содержит другой класс (Компонент), но:
1. Компонент может существовать независимо от контейнера.
2. Компонент передаётся извне (не создаётся внутри контейнера).

```csharp
class Department {
    public string Name { get; set; }
    public Department(string name) => Name = name;
}

class University {
    // Агрегация: University содержит Department, но Department может существовать без University
    public List<Department> Departments { get; set; }

    public University() {
        Departments = new List<Department>();
    }

    public void AddDepartment(Department department) {
        Departments.Add(department);
    }
}

// Использование
var mathDept = new Department("Математика");
var physicsDept = new Department("Физика");

var university = new University();
university.AddDepartment(mathDept);  // Department передаётся извне
university.AddDepartment(physicsDept);

// Даже если университет удалён, кафедры останутся
university = null;
Console.WriteLine(mathDept.Name);  // "Математика" — объект жив
```


Осведомлённость — это когда один класс знает о существовании другого, но не управляет его жизненным циклом.
Обычно реализуется через:
1. Передачу ссылки в метод или конструктор.
2. Подписку на события другого объекта.

Пример 1. Передача ссылки в метод или конструктор
```csharp
class Database {
    public string GetData(int id) => $"Данные #{id}";
}

class Cache {
    private Dictionary<int, string> _cachedData = new();

    // Cache осведомлён о Database, но не управляет им
    public string GetData(Database db, int id) {
        if (!_cachedData.TryGetValue(id, out var data)) {
            data = db.GetData(id);  // Запрашиваем данные из БД
            _cachedData[id] = data;
        }
        return data;
    }
}

// Использование
var db = new Database();
var cache = new Cache();

Console.WriteLine(cache.GetData(db, 1));  // Загрузит из БД
Console.WriteLine(cache.GetData(db, 1));  // Вернёт из кэша
```

Пример 2. Осведомленность через события
```csharp
class Sensor {
    public event Action<int>? TemperatureChanged;

    public void SimulateChange() {
        TemperatureChanged?.Invoke(25);  // Уведомляем подписчиков
    }
}

class Logger {
    // Logger осведомлён о Sensor через подписку
    public void Subscribe(Sensor sensor) {
        sensor.TemperatureChanged += temp =>
            Console.WriteLine($"Зафиксировано изменение: {temp}°C");
    }
}

// Использование
var sensor = new Sensor();
var logger = new Logger();

logger.Subscribe(sensor);  // Logger теперь "знает" о Sensor
sensor.SimulateChange();   // Выведет: "Зафиксировано изменение: 25°C"
```


Типичные причины, по которым приходится перепроектировать систему:

1. При создании объекта явно указывается класс. Задание имени класса
   привязывает вас к конкретной реализации, а не к конкретному интерфейсу. Это может осложнить изменение объекта в будущем. Чтобы уйти
   от такой проблемы, создавайте объекты косвенно

Паттерны проектирования: абстрактная фабрика (113), фабричный метод
(135), прототип (146);

2. Зависимость от конкретных операций. Задавая конкретную операцию,
   вы ограничиваете себя единственным способом выполнения запроса.
   Если же не включать запросы в код, то будет проще изменить способ
   удовлетворения запроса как на этапе компиляции, так и на этапе выполнения.

Паттерны проектирования: цепочка обязанностей (263), команда (275);

3. Зависимость от аппаратной и программной платформ. Внешние интерфейсы операционной системы и интерфейсы прикладных программ
   (API) различны на разных программных и аппаратных платформах.
   Если программа зависит от конкретной платформы, ее будет труднее
   перенести на другие. Возможно, даже на «родной» платформе такую
   программу трудно поддерживать. Поэтому при проектировании систем
   так важно ограничивать платформенные зависимости.

Паттерны проектирования: абстрактная фабрика (113), мост (184);

4. зависимость от представления или реализации объекта. Если клиент
   располагает информацией о том, как объект представлен, хранится или
   реализован, то, возможно, при изменении объекта придется изменять
   и клиента. Сокрытие этой информации от клиентов поможет уберечься
   от каскадных изменений.
   Паттерны проектирования: абстрактная фабрика (113), мост (184), хранитель (330), заместитель (246);

5. зависимость от алгоритмов. Во время разработки и последующего использования алгоритмы часто расширяются, оптимизируются и заменяются.
Зависящие от алгоритмов объекты придется переписывать при
   каждом изменении алгоритма. Поэтому алгоритмы, которые с большой
   вероятностью будут изменяться, следует изолировать.
   Паттерны проектирования: мост (184), итератор (302), стратегия (362),
   шаблонный метод (373), посетитель (379);

6. сильная связанность. Сильно связанные между собой классы трудно использовать порознь, так как они зависят друг от друга. Сильная связанность приводит к появлению монолитных систем, в которых нельзя ни
   изменить, ни удалить класс без знания деталей и модификации других
   классов. Такую систему трудно изучать, переносить на другие платформы и сопровождать.
   Слабая связанность повышает вероятность того, что класс можно будет
   повторно использовать сам по себе. При этом изучение, перенос, модификация и сопровождение системы намного упрощаются. Для поддержки
   слабосвязанных систем в паттернах проектирования применяются такие
   методы, как абстрактные связи и разбиение на слои
   Паттерны проектирования: абстрактная фабрика (113), мост (184), цепочка обязанностей (263), команда (275), фасад (221), посредник (319),
   наблюдатель (339);

7. неудобства при изменении классов. Иногда нужно модифицировать
   класс, но делать это неудобно. Допустим, вам нужен исходный код, а он
   недоступен (так обстоит дело с коммерческими библиотеками классов).
   Или любое изменение тянет за собой модификации множества существующих подклассов. Благодаря паттернам проектирования можно
   модифицировать классы и при таких условиях.
   Паттерны проектирования: адаптер (171), декоратор (209), посетитель (379).
