Глава 2. Проектирование редактора документов

Внутреннее представление должно поддерживать:
1. Отслеживание физической структуры документа, то есть разбиение текста и графики на строки, колонки, таблицы и тд;
2. Генерирование визуального представления документа
3. Установление соответствия между позициями экрана и элементами внутреннего представления. Это позволит определить, что имеет в виду пользователь,
выбирая некоторый элемент визуального представления

Ограничения:
- Текст и графику следует трактовать единообразно. Интерфейс должен позволять свободно размещать текст
внутрь графики и наоборот. Не следует считать графику частным случаем текста или наоборот, поскольку
это в конечном счете приведет к появлению избыточных механизмов форматирования и манипулирования.
Одного набора механизмов достаточно и для текста и для графики.

**Рекурсивная композиция**

Рекурсивная композиция — это подход в ООП и проектировании систем, при котором объекты состоят из
других объектов того же типа, образуя древовидную или иерархическую структуру. Этот принцип
часто используется в паттернах проектирования, таких как Компоновщик (Composite).
Пример с формированием Json в **JsonConverterWithRecursiveComposition**

Конкретно по данной книге:
Представляя объектом каждый символ и каждый графический элемент документа, мы обеспечиваем
гибкость на самых нижних уровнях дизайна Lexi.
Текст и графика обрабатываются единообразно в том, что касается отображения, форматирования и вложения друг в
друга. Lexi можно расширить для поддержки новых наборов символов, не затрагивая никаких других функций.
Объектная структура Lexi точно отражает физическую структуру документа


У описанного подхода есть два важных следствия. Первое очевидно: для
объектов нужны соответствующие классы. Второе, менее очевидное, состоит
в том, что у этих классов должны быть совместимые интерфейсы, поскольку
мы хотим унифицировать работу с ними. Для обеспечения совместимости
интерфейсов в таком языке, как C++, применяется наследование.


**Глифы**

Глиф — это визуальное представление символа (буквы, цифры, знака препинания или иконки) в определённом
шрифте или графической системе. Это не сам символ, а его конкретное графическое воплощение с уникальными характеристиками:
1. Форма (контуры, засечки, толщина линий)
2. Размер (высота, ширина, кернинг)
3. Стиль (курсив, жирность, декоративные элементы)


В .NET для работы с глифами используется пространство имён System.Windows.Media:
```csharp
using System.Windows.Media;

// Получение глифов из шрифта
GlyphTypeface font = new GlyphTypeface(new Uri("C:/Fonts/arial.ttf"));
ushort glyphIndex = font.CharacterToGlyphMap['A']; // Индекс глифа для 'A'

// Создание визуального представления текста
var glyphRun = new GlyphRun(
    font,
    0,          // Размер шрифта
    false,      // Поддержка RTL
    1.0,        // Масштаб
    new[] { glyphIndex },
    new Point(0, 0),
    new[] { 10.0 }, // Ширина глифов
    null, null, null, null, null, null);
```


Базовый интерфейс класса Glyph определяется для всех объектов, которые могут присутсовать в структуре
документа. Его подклассы определяют как примитивные графические элементы (символы и озображения), так и
структурные элементы (строчки и колонки).

В базовом интерфейсе нужно отразить обязанности: внешнего представления (Draw, Bounds), обнаружение
точки воздействия (Intersects), структура (Insert, Remove, Child, Parent).

Глифы умеют рисовать себя на кране, знают сколько места занимают, а так же располагают информацией о своих
потомках и родителях.

**Паттерн Composite (компоновщик)**
Рекурсивная композицияи подходит не только для документов. Ей можно пользоваться для представления любых
потенциально сложных иерархических структура. Паттерн компоновщик инкапсулирует сущность рекурсивной
композиции в объектов-ориентированных категориях.

![](../Images/composition_compositor.png)



**Паттерн Стратегия**
Инкапсуляция алгоритма в объект. Ключ к применению паттерна стратегия - проектирование интерфейсов стратегии
и контекста, достаточно общих для поддержки широкого диапазона алгоритмов.


Композиция с одним потомком и совместимые интерфейсы. В общем случае клиенту неизвестно, имеет ли он дело
с компонентом или его окружением (то есть родителем), особенно если окружение просто делегирует все операции
своему единственному компоненту. Но окружение может также расширять поведение компонента, выполняя дополнительные
действия либо до, либо после делегирования (а возможно, и до, и после). Окружение может также добавить компоненту
состояние.

**Инкапсуляция зависимостей от реализации**
Нужно отделить функциональность приложения от аппаратной платформы. Для этого например для класса Window будет инкапсулировать
функциональность окна в любой оконной системе: операции прорисовки базовых геометрических фигур, возможность свернуть и
развернуть окно, изменение собственных размеров, перерисовка своего содержимого при необходимости.

**Паттерн Bridge (мост)**

Операции пользователя: создание нового документа; открытие, сохранение и печать существующего документа; вырезание
выбранной части документа и вставка ее в другое место;
изменение шрифта и стиля выбранного текста;
измененеия форматирования текста (например, установка режима выравнивания);
завершение работы приложения и тд

Теперь в классе MenuItem может храниться объект, инкапсулирующий запрос (рис. 2.12). Каждому объекту,
представляющему пункт меню, передается экземпляр того из подклассов Command, который соответствует этому
пункту, точно так же, как мы задаем текст, отображаемый в пункте меню.
Когда пользователь выбирает некоторый пункт меню, объект MenuItem просто вызывает операцию Execute для своего
объекта Command, чтобы он выполнил запрос. Заметим, что кнопки и другие видже ты могут пользоваться
объектами Command точно так же, как и пункты меню.


**Паттерн Command (Команда)**
Команда — это поведенческий паттерн, который инкапсулирует запрос в виде объекта, позволяя:
Параметризировать клиенты различными запросами.
Ставить запросы в очередь, логировать или отменять их.
Поддерживать отмену операций (undo/redo).
