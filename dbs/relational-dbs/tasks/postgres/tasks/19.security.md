# Глава 19. Безопасность данных

## Теория

Вот «золотой стандарт» (принцип Парето) по безопасности в PostgreSQL. Если вы поймете эти 4 концепции, вы решите все 5 задач.

### 1. Роли vs Пользователи
В PostgreSQL **нет разницы** между пользователем и группой. Это всё — **ROLES**.
*   Чтобы роль могла **входить** в базу: `CREATE ROLE name LOGIN;`
*   Чтобы роль была просто **группой прав** (шаблоном): `CREATE ROLE name;` (без LOGIN).
*   **Наследование:** `GRANT group_role TO user_role;` — пользователь мгновенно получает все права группы.

> **Лайфхак:** Создайте одну роль-группу с правами `SELECT`. Создайте пользователя с `LOGIN`. Добавьте пользователя в группу. Готово.

### 2. Правило двух ключей: Схема + Таблица (Для задачи 19.3)
Чтобы прочитать таблицу, нужно **два** разрешения. Забывание первого — причина 90% ошибок.
1.  **Ключ от подъезда (Schema):** `GRANT USAGE ON SCHEMA public TO role;` (Без этого вы даже не увидите таблицы).
2.  **Ключ от квартиры (Table):** `GRANT SELECT ON TABLE my_table TO role;` (Без этого вы увидите таблицу, но не данные).

### 3. RLS: Фильтр, а не запрет (Для задач 19.4, 19.5)
Row-Level Security (RLS) не запрещает доступ к таблице. Он добавляет невидимый `WHERE` к каждому вашему запросу.
*   Включается одной командой: `ALTER TABLE t ENABLE ROW LEVEL SECURITY;`
*   По умолчанию, если включили RLS, но не создали политик — **никто ничего не видит** (даже владелец, кроме суперюзера).

### 4. Как обмануть систему (Идентификация приложения) (Для задач 19.4, 19.5)
База данных видит только технического пользователя (например, `app_user`). Она не знает, что сейчас сайт открыл Вася.
Как передать имя Васи в базу для RLS?
1.  Приложение выполняет: `SET app.current_id = 'vasya';`
2.  В политике RLS вы читаете это значение: `current_setting('app.current_id')`.

#### Для 19.4 (RLS для "виртуальных" юзеров):
```sql
-- 1. Включаем фильтр
ALTER TABLE tickets ENABLE ROW LEVEL SECURITY;

-- 2. Создаем правило: "Видеть только свои билеты"
CREATE POLICY user_tickets_policy ON tickets
FOR SELECT
USING (
    -- Сравниваем колонку в таблице с переменной сессии
    passenger_id = current_setting('app.passenger_id')::text
);

-- 3. Как использовать из приложения:
-- SET app.passenger_id = 'IVANOV';
-- SELECT * FROM tickets; -- Вернет только билеты Иванова
```

#### Для 19.5 (Уровни доступа):
Создайте таблицу-справочник `access_levels(user_id, level)`.
В политике используйте подзапрос:
```sql
CREATE POLICY secret_policy ON docs
FOR SELECT
USING (
    doc_level <= (
        SELECT level 
        FROM access_levels 
        WHERE user_id = current_setting('app.user_id')::int
    )
);
```
*(Логика: если у меня уровень допуска 5, я вижу документы с уровнем секретности 1, 2, 3, 4, 5).*

## 19.1

Создайте роль для доступа на чтение к демонстрационной базе данных без права создания сеансов работы с сервером БД.

Мы создаем роль для доступа, но не даем возможность Login

```sql
CREATE ROLE read_only_group;

GRANT USAGE ON SCHEMA bookings TO read_only_group;

GRANT SELECT ON ALL TABLES IN SCHEMA bookings TO read_only_group;
```

## 19.2

Создайте пользователя сервера БД и предоставьте ему привилегию использования роли, созданной в предыдущем упражнении. Проверьте, что этот пользователь может выполнять любые запросы на выборку из таблиц демонстрационной базы данных, но не может их обновлять.

```sql
CREATE ROLE app_user LOGIN PASSWORD '123';
GRANT read_only_group TO app_user;
```

Проверка доступа:

```text
psql -h localhost -d demo -U app_user

select * from bookings limit 1; - доступ есть

update bookings set total_amount = total_amount + 1 where book_ref = '756UAS';
-- ERROR:  permission denied for table bookings
```

## 19.3

Постройте пример, показывающий, что для доступа к таблицам схемы необходимо также предоставить право использования (USAGE) этой схемы.

Отбираем права на Schema bookings И видим, что больше нет доступа на чтение:

```sql
REVOKE ALL ON SCHEMA bookings FROM app_user; -- такой вариант не работает, тк отзываются только права пользователя, а мы выдавали права на группу


-- отзываем права на select
REVOKE SELECT ON ALL TABLES IN SCHEMA bookings FROM read_only_group;

demo=> select * from bookings limit 1;
-- ERROR:  permission denied for table bookings

-- возвращаем права на select и select проходит
GRANT SELECT ON ALL TABLES IN SCHEMA bookings TO read_only_group;


-- отзываем права на usage
REVOKE USAGE ON SCHEMA bookings FROM read_only_group;

demo=> select * from bookings limit 1;
ERROR:  relation "bookings" does not exist
```

## 19.4

Реализуйте схему разграничения доступа на уровне строк для пользователей уровня приложения (не зарегистрированных как пользователи на сервере базы данных).

```sql
-- создадим таблицу с личными данными (например, заказы)
CREATE TABLE app_orders (
    id serial PRIMARY KEY,
    customer_name text,
    order_details text,
    app_user_id text
);

INSERT INTO app_orders (customer_name, order_details, app_user_id) VALUES
('Ivan', 'Laptop', 'user_ivan'),
('Maria', 'Phone', 'user_maria'),
('Ivan', 'Mouse', 'user_ivan');

-- Включаем RLS для таблицы
ALTER TABLE app_orders ENABLE ROW LEVEL SECURITY;

-- Создаем политику
CREATE POLICY user_isolation_policy ON app_orders
FOR SELECT
USING (
    app_user_id = current_setting('app.current_user_id', true)
    -- true во втором аргументе current_setting означает: если переменная не установлена, вернуть NULL, а не ошибку.
);

SET ROLE app_user; -- Переключаемся на нашего технического юзера
SELECT * FROM app_orders; 
-- Результат: 0 строк, так как current_setting вернет NULL

-- имитация входа Ивана
SET app.current_user_id = 'user_ivan';
SELECT * FROM app_orders;
-- Результат: 2 строки (Laptop и Mouse)
```
