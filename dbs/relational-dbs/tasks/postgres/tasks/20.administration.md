## 20.3

Подумайте, какие индексы было бы полезно создать, чтобы ускорить выполнение запросов из упражнений к главе 4. Проверьте ваши предположения.


### 1 запрос

```sql
SELECT * FROM flights
WHERE scheduled_arrival < flights.actual_arrival
```

Такой запрос к сожалению не получится оптимизировать, тк условие зависит от значений внутри каждой строки, а не от поиска конкретного значения

### 2 запрос

```sql
SELECT t.passenger_name 
FROM tickets t
JOIN segments s on t.ticket_no = s.ticket_no
WHERE s.fare_conditions = 'Economy'
AND s.price > 70000
```

Этот запрос в теории можно улучшить индексом на segments (fare_conditions, price), но надо смотреть по селективности, будет ли планировщик его улучшать

### 3 запрос

```sql
SELECT 
    bp.seat_no, t.passenger_name, f.scheduled_departure, f.scheduled_arrival,
    r.departure_airport, r.arrival_airport
FROM boarding_passes bp
JOIN tickets t on bp.ticket_no = t.ticket_no
JOIN flights f on bp.flight_id = f.flight_id
JOIN routes r on f.route_no = r.route_no
WHERE f.status NOT IN ('Arrived', 'Cancelled', 'Departed')
```

В запросе присутствует аж 4 таблички. Тут сразу же стоит задуматься о денормализации: вынести status из flight в tickets, которые будут обновляться с eventual consistency, плюсом в рейс можно вынести аэропорты вылета и прилета, чтобы не надо было каждый раз делать join на routes

По запросу видно, что происходит seq scan по flights, после hash join на seq scan boarding passes по flights id (нужен индекс по flight_id), после происходит hash join на tickets (нужен индекс по ticket_no), также нужен индекс на routes.route_no

## 4 запрос

```sql
SELECT t.passenger_name, s.flight_id 
FROM flights f
JOIN segments s ON s.flight_id = f.flight_id
JOIN tickets t on t.ticket_no = s.ticket_no
LEFT JOIN boarding_passes bp ON f.flight_id = bp.flight_id
WHERE f.scheduled_departure >= '2025-12-07' -- тут нет индекса, поэтому используется seq scan
AND f.scheduled_departure < '2025-12-08'
AND bp.boarding_no IS NULL;
```

## 5 запрос

```sql
SELECT AVG(s.price) 
FROM segments s
JOIN flights f on s.flight_id = f.flight_id
JOIN routes r on f.route_no = r.route_no -- это соединение происходило с seq scan по flights и дальнейшим hash join
WHERE r.departure_airport = 'VOZ' AND r.arrival_airport = 'LED';
```

Добавление индекса:
```sql
CREATE INDEX CONCURRENTLY "flights_route_no"
  ON flights(route_no);
```

Упрощение запроса, путем удаления необходимости делать Seq Scan по flights

```text
Aggregate
  ->  Nested Loop
        ->  Nested Loop
              ->  Index Scan using routes_departure_and_arrival on routes r
                    Index Cond: ((departure_airport = 'VOZ'::bpchar) AND (arrival_airport = 'LED'::bpchar))
              ->  Bitmap Heap Scan on flights f
                    Recheck Cond: (r.route_no = route_no)
                    ->  Bitmap Index Scan on flights_route_no
                          Index Cond: (route_no = r.route_no)
        ->  Index Scan using segments_flight_id_idx on segments s
              Index Cond: (flight_id = f.flight_id)
```

## 20.4

Дан следующий запрос к демобазе:

```sql
SELECT *
FROM tickets t
WHERE to_tsvector(t.passenger_name) @@ to_tsquery('PAVEL & IVANOV')
AND bookings.now() - interval '10 days' < (
    SELECT b.book_date
    FROM bookings b
    WHERE upper(b.book_ref) = upper(t.book_ref)
);
```


Перепишите его с учетом замечаний, сформулированных в разделе 20.5.3.
Сравните скорость выполнения запроса до и после модификации.

Главные проблемы: 
1. Использование fts, хотя можно обойтись обычным =
2. использование Upper на bookings, который мешает использованию индекса

Исправленный запрос:

```
SELECT t.* 
FROM tickets t
JOIN bookings b on b.book_ref = t.book_ref
WHERE t.passenger_name = 'PAVEL IVANOV'
AND bookings.now() - make_interval(days := 10) < b.book_date
```

Можно исправить seq scan с помощью создания индекса на passenger_name.

```text
Nested Loop  (cost=0.43..68087.28 rows=2 width=52)
  ->  Seq Scan on tickets t  (cost=0.00..67918.27 rows=20 width=52)
        Filter: (passenger_name = 'PAVEL IVANOV'::text)
  ->  Index Scan using bookings_pkey on bookings b  (cost=0.43..8.45 rows=1 width=7)
        Index Cond: (book_ref = t.book_ref)
        Filter: (('2025-12-01 00:00:00+00'::timestamp with time zone - '10 days'::interval) < book_date)

```

## 20.5

Опишите конфигурацию системы, имеющей запасной сервер в теплом резерве, и составьте инструкцию по восстановлению работоспособности системы в случае разрушения носителя на основном сервере.


Холодный резерв - сервер выключен или на наем просто стоит ОС. Бэкапы копируются раз в сутки/неделю. Восстановление занимает часы
Теплый резерв - сервер включен, postgres запущен в режиме standby. Он постоянно доигрывает WAL логи с основного сервера. Отставание может составлять от нескольких секунд до минут. ДЛя включения нужно выполнить команду promote
Горящий резерв - то же самое, что теплый, но сервер доступен только для чтения прямо сейчас. Переключение на запись происходит мгновенно. В современном postgres термины Warm и Hot часто сливаются, так как Stanby сервер может обслуживать SELECT запросы, пока ждет переключения
