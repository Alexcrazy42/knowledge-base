# Глава 18. Полнотекстовый поиск

to_tsvector - отсортированный список лексем (нормализованных слов) с позициями внутри документа

```sql
SELECT to_tsvector('english', 'The quick brown fox jumps over the lazy dog');
-- 'brown':3 'dog':9 'fox':4 'jump':5 'lazi':8 'quick':2 норрмализованные слова
```

текст → Parser → Tokens → Dictionary (нормализация + стоп-слова) → tsvector

to_tsquery - поисковый запрос, тоже из лексем, но с логическими операторами

```sql
SELECT to_tsquery('english', 'quick & (fox | cat) & !dog');
-- 'quick' & ( 'fox' | 'cat' ) & !'dog'
```

Для FTS подходит два типа индексов - GIN и GiST

## GIN (Gemerlized Inverted Index)

Инвертированный индекс - классическая структура для хранения (лексема → posting list [(ctid, positions, weight), ...])

В отличии от B-дерева, которое отвечает на вопрос "где находится значение X?", инвертированный индекс отвечает на вопрос "в каких документах встречается термин T?".

Posting list - список документов с позициями вхождений:

```text
"поиск"    → {doc_3: [5, 12], doc_7: [1], doc_15: [8, 22, 40]}
"полный"   → {doc_3: [4], doc_15: [7]}
"текст"    → {doc_1: [3], doc_3: [6], doc_9: [2]}
```

Плюсы:  очень быстрый поиск по вхождению лексем. Идеален для запросов вида tsvector @@ tsquery
Минусы: медленное обновление (каждая лексема = несколько записей в индексе), большой размер (в 2-3 раза больше данных), не умеет ранжировать без обращения к таблице
Под капотом: B-tree по ключу-лексеме, значения - posting list-ы, сжатиые через varbyte-encoding. Поддерживает fastupdate (буферизацию новых записей в pending list, которая помтом мержится в основной индекс - критично для write-heavy нагрузок)

Выбирать для read-heavy, когда важна точность и скорость поиска (большинство случаев)

## GiST (Generalized Search Tree)

Хранит сигнатуры - битовые векторы (2048 бит по умолчанию), где каждая лексема хешируется в позицию бита

Плюсы: маленький размер, быстрое обновление, можно делать nearest-neighbor поиск (полезно для ORDER BY ts_rank с LIMIT)
Минусы: возможны false positives, нужна дофильтрация по оригинальному tsvector
Под капотом: R-tree подобная структура, в узлах - объединенные сигнатуры потомков (побитовое OR)

Выбирать для write-heavy или когда нужен поиск с LIMIT и ORDER BY rank (top-N)

## Ранжирование

FTS не просто возвращает "найдено/не найдено", а сортирует результаты по релевантности. ДЛя этого используются математические модели:

TF-IDF - Чем чаще термин в документе (TF) и чем реже во всей коллекции (IDF), тем выше вес
BM25 - Улучшенная версия TF-IDF: учитывает длину документа и насыщение частоты (стандарт де-факто)
Векторный поиск- Документы и запросы представляются как векторы в многомерном пространстве; близость = семантическое сходство
Learning to Rank - ML-модель, обученная на кликах/оценках пользователей, комбинирует десятки сигналов

ts_rank - простая TF-based метрика: учитывает частоту вхождений, weight-ы, нормализацию по длине документа
ts_rank_cd - cover density: учитывает, насколько близко друг к другу находятся слова запроса. Требует, чтобы в tsvector были позиции (они там по умолчанию есть)

Пример:

```sql
SELECT title, ts_rank_cd(tsv, query, 32) AS rank
FROM articles, plainto_tsquery('english', 'quantum computing') query
WHERE tsv @@ query
ORDER BY rank DESC
LIMIT 10;
```

## 18.2

Выполните то же самое, что и в предыдущем упражнении, но таблица должна содержать документы на разных языках

Впринципе можно заиспользовать триграммы, для задачи с именами, этого вполне достаточно будет. Но тк изначальная задача связана с текстами, то нужен будет именно fts, тк только он "понимает" текст через стемминг, лексемизацию.

Но мы не можем построить индекс по tsvector без указания языка, тк tsvector зависит от текущего параметра default_text_search_config и это не является immutable функцией (postgres умеет строить индексы только по immutable)

Самым простым решением может показаться - создать индекс на колонку для каждого языка, но тут сразу возникают проблемы - большое кол-во места под эти индексы, нужно знать какой язык используется + если в одном документе несколько языков - проблема.

Можно использовать Simple конфигурацию, игнорируя нормализацию, но вариант не подходит если недопустим мусор и низкая точность.

Я бы такой кейс впринципе не держал в Postgres, а вынес в Elastic

Напишите выражение, которое построит текстовое представление для бронирования, выбирая информацию о времени отправления и прибытия, типе самолета, аэропортах и населенных пунктах отправления и прибытия. Выполните поиск рейсов, вылетающих из Шереметьево в определенный день, с помощью текстового поиска и обычного SQL-запроса. Сравните время выполнения.


Создание представления:
```sql
CREATE MATERIALIZED VIEW booking_search_view AS
SELECT
    b.book_ref,
    b.book_date,
    f.scheduled_departure,
    f.scheduled_arrival,
    r.departure_airport,
    r.arrival_airport,
    to_tsvector(
        'english',
        string_agg(
            DISTINCT
            to_char(f.scheduled_departure, 'YYYY-MM-DD') || ' ' ||
            (air.model->>'en') || ' ' ||
            (dep.city->>'en') || ' ' ||
            (arr.city->>'en'),
            ' '
        )
    ) AS search_document
FROM bookings b
JOIN tickets t ON b.book_ref = t.book_ref
JOIN segments s ON s.ticket_no = t.ticket_no
JOIN flights f ON s.flight_id = f.flight_id
JOIN routes r ON r.route_no = f.route_no
JOIN airplanes_data air ON air.airplane_code = r.airplane_code
JOIN airports_data dep ON dep.airport_code = r.departure_airport
JOIN airports_data arr ON arr.airport_code = r.arrival_airport
GROUP BY b.book_ref, b.book_date, f.scheduled_departure, f.scheduled_arrival, r.departure_airport, r.arrival_airport;
```

```sql
CREATE INDEX idx_booking_search_gin ON booking_search_view USING GIN (search_document);
```

```sql
SELECT book_ref, scheduled_departure, search_document
FROM booking_search_view
WHERE search_document @@ to_tsquery('english', '2026-05-25 & SVO');
```
