## Пример транзакции

### 6.1 Упражнение

Начните транзакцию командой BEGIN и создайте новое бронирование в таблице bookings сегодняшней датой. Добавьте два электронных билета в таблице tickets, связанных с созданным бронированием.
Представьте, что пользователь не подтвердил бронирование и все введенные данные необходимо отменить. Выполнитье отмену транзакции и проверьте, что никакой добалавнной вами информации действительно не осталось. 

Procedure:

```sql
CREATE OR REPLACE PROCEDURE bookings.create_booking_and_tickets(
    p_book_ref VARCHAR(6),
    p_passenger1_id VARCHAR(13),
    p_passenger1_name TEXT,
    p_passenger2_id VARCHAR(13),
    p_passenger2_name TEXT
)
LANGUAGE plpgsql
AS $$
DECLARE
    v_ticket_no1 VARCHAR(13);
    v_ticket_no2 VARCHAR(13);
BEGIN
    v_ticket_no1 := '0005434990768';
    v_ticket_no2 := '0005434990769';
    

    INSERT INTO bookings.bookings (
        book_ref,
        book_date,
        total_amount
    ) VALUES (
        p_book_ref,
        CURRENT_DATE,
        0
    );
    
    INSERT INTO bookings.tickets (
        ticket_no,
        book_ref,
        passenger_id,
        passenger_name,
        outbound
    ) VALUES (
        v_ticket_no1,
        p_book_ref,
        p_passenger1_id,
        p_passenger1_name,
        false
    );
    
    INSERT INTO bookings.tickets (
        ticket_no,
        book_ref,
        passenger_id,
        passenger_name,
        outbound
    ) VALUES (
        v_ticket_no2,
        p_book_ref,
        p_passenger2_id,
        p_passenger2_name,
        false
    );
    
    RAISE NOTICE 'Создано бронирование: %, билеты: % и %', 
                  p_book_ref, v_ticket_no1, v_ticket_no2;
    
EXCEPTION
    WHEN OTHERS THEN
        RAISE NOTICE 'Ошибка: %', SQLERRM;
        ROLLBACK;
        RAISE;
END;
$$;
```


Call:

```sql
CALL bookings.create_booking_and_tickets(
    'XC789Z',
    '1234567890123', 'IVAN PETROV',
    '9876543210987', 'MARIA PETROVA'
);

SELECT * FROM bookings.bookings WHERE book_ref = 'XC789Z';
SELECT * FROM bookings.tickets WHERE book_ref = 'XC789Z';

ROLLBACK;
```

## Уровень изоляции Read Committed

### 6.4. Упражнение

Перед началом выполнения задания проверьте, что в таблице bookings нет бронирований на сумму total_amount 1000 рублей.

- в первом сеансе начните транзакцию. Выполните обновление таблицы bookings: увеличьте total_amount в два раза в тех строках, где сумма равна 1000 рублей
- во втором сеансе (откройте новое окно psql) вставьте в таблицу bookings новое бронирование на 1000 рублей и зафиксируйте транзакцию
- в первом сеансе повтоорите обновление таблицы bookings и зафиксируйте транзакцию

Осталась ли сумму добавленного бронирования равным 1000 рублей? Почему это не так?

Ответ: будет обновлено, тк на уровне Read Committed не делается снапшота, а видятся закомиченные изменения, как в Repeatable Read, что грозит аномалией "Неповторяемое чтение".

```sql
1 - BEGIN;
2 - BEGIN;

1 - UPDATE bookings SET total_amount = total_amount * 2 WHERE total_amount = 1000; -- ноль обновленных строк

2 - INSERT INTO bookings (book_ref, book_date, total_amount) VALUES ('2EW1S4', '2025-09-01 03:00:12.557 +0300', 1000);
2 - COMMIT;

1 - UPDATE bookings SET total_amount = total_amount * 2 WHERE total_amount = 1000; -- одна обновленная строка
2 - SELECT * FROM bookings WHERE book_ref = '2EW1S4'; -- total_amount = 2000
1 - COMMIT;
```

## Уровень изоляции Serializable

### 6.7 Упражнение

Повторите предыдущие упражнения, но транзакции в обоих сеансах с уровнем изоляции Serialiazble. 

Если вы правильно ответили на его последний вопрос, вы поймете, почему теперь эти действия приводят к ошибке. Если же результат этого упражнения стал для вас неожиданностью, четко сформулируйте различие уровней Repeatable Read и Serializable

При Serializable получаем ошибку для второй по счету попытки сделать Commit: 

ERROR:  could not serialize access due to read/write dependencies among transactions
ПОДРОБНОСТИ:  Reason code: Canceled on identification as a pivot, during commit attempt.
ПОДСКАЗКА:  The transaction might succeed if retried

#### Четкая разница между Repeatable Read и Serializable

Repeatable Read - нельзя увидеть изменения в уже существующих строках, можно увидеть новые строки (фантомы), добавленных другой транзакцией

Serializable - нельзя увидеть вообще ничего, что сделала другая транзакция после начала текущей (ни изменения, ни новые строки)

В обоих уровнях не будет фантомного чтения, но Serializable накладывает ограничения на паралелльные транзакции и выкидывается ошибку.

## Вложенных транзакции

### 6.8 Упражнение

Некоторые СУБД (но не pg) позволяют использовать вложенных транзакции. Если начать вторую транзакцию, не завершая открытую первую, то вторая транзакция будет считаться вложенной: ее результат фиксируется только в том случае, если фиксируется первая транзакция, но при этом ее рузльтаты можно отменить независимо от первой транзакции.

Реализуйте такое поведение для PG, т.е предложите, какие команды следует выполнить для открытия вложенной транзакции, для ее отмены и для фиксации. Подсказка: используйте оператор SAVEPOINT


```sql
-- 1. Начинаем внешнюю (основную) транзакцию
BEGIN;

-- Вставляем данные во внешней транзакции
INSERT INTO bookings.bookings (book_ref, book_date, total_amount)
VALUES ('OUTER0', CURRENT_DATE, 1000);

-- ========================================
-- 2. НАЧАЛО вложенной транзакции
SAVEPOINT nested_sp;

-- Вставляем данные во вложенной транзакции
INSERT INTO bookings.tickets (ticket_no, book_ref, passenger_id, passenger_name, outbound)
VALUES ('1111111111111', 'OUTER0', '1234567890123', 'NESTED PASSENGER', false);

-- Проверяем: данные вложенной транзакции видны
SELECT * FROM bookings.tickets WHERE book_ref = 'OUTER0';  -- покажет билет
-- ========================================

-- 3. ОТМЕНА вложенной транзакции (аналог ROLLBACK)
ROLLBACK TO SAVEPOINT nested_sp;

-- Теперь билета нет
SELECT * FROM bookings.tickets WHERE book_ref = 'OUTER0';  -- пусто

-- ========================================
-- 4. Новая вложенная транзакция с другим именем
SAVEPOINT nested_sp2;

INSERT INTO bookings.tickets (ticket_no, book_ref, passenger_id, passenger_name, outbound)
VALUES ('2222222222222', 'OUTER0', '9876543210987', 'ANOTHER PASSENGER', false);

-- 5. ФИКСАЦИЯ вложенной транзакции (аналог COMMIT)
RELEASE SAVEPOINT nested_sp2;

-- Данные сохранились, но точка удалена
SELECT * FROM bookings.tickets WHERE book_ref = 'OUTER0';  -- показывает билет
-- ========================================

-- 6. Фиксируем внешнюю транзакцию
COMMIT;
```
