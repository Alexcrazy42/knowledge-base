# EXPLAIN ANALYZE в PostgreSQL: Полное руководство

## Введение

`EXPLAIN ANALYZE` — это главный инструмент оптимизации запросов в PostgreSQL. Он показывает **реальный** план выполнения запроса с фактическими затратами времени и количеством строк, в отличие от обычного `EXPLAIN`, который даёт только оценку планировщика.

---

## Синтаксис

```sql
EXPLAIN [ANALYZE] [VERBOSE] [BUFFERS] [TIMING] [SUMMARY] [FORMAT {TEXT | XML | JSON | YAML}]
    { SELECT | INSERT | UPDATE | DELETE }
```

### Ключевые опции

| Опция | Назначение |
|-------|------------|
| `ANALYZE` | Выполняет запрос и показывает реальные значения (время, строки) |
| `VERBOSE` | Показывает дополнительные детали (список выводимых колонок) |
| `BUFFERS` | Показывает использование буферного кэша (чтение/запись страниц) |
| `TIMING` | Включить/выключить замер времени (по умолчанию включён с ANALYZE) |
| `SUMMARY` | Показывает суммарную статистику (время планирования, время выполнения) |

### Примеры использования

```sql
-- Базовый план выполнения (оценка)
EXPLAIN SELECT * FROM tickets WHERE book_ref = 'TEST02';

-- Реальный план с временем выполнения
EXPLAIN ANALYZE SELECT * FROM tickets WHERE book_ref = 'TEST02';

-- Детальный анализ с буферами
EXPLAIN (ANALYZE, BUFFERS, VERBOSE, FORMAT JSON)
SELECT * FROM tickets WHERE book_ref = 'TEST02';
```

## Узлы плана выполнения

### 📥 Узлы выборки данных (Scan узлы)

| Узел | Описание | Когда используется |
|------|----------|---------------------|
| **Seq Scan** | Последовательное сканирование всей таблицы (читает все страницы) | Когда нужно прочитать большую часть таблицы (>5-10%) или нет подходящего индекса |
| **Index Scan** | Сканирование индекса с обращением к таблице по указателям | Когда индекс селективен и нужно прочитать мало строк |
| **Index Only Scan** | Сканирование только индекса (все данные в индексе, без обращения к таблице) | Когда индекс содержит все запрошенные колонки (покрывающий индекс) |
| **Bitmap Index Scan** | Построение битовой карты страниц по индексу | Первый этап Bitmap-сканирования |
| **Bitmap Heap Scan** | Чтение таблицы по битовой карте страниц | Второй этап Bitmap-сканирования (эффективно для "средней" селективности) |
| **Tid Scan** | Прямой доступ к строке по физическому адресу (ctid) | При использовании `WHERE ctid = ...` |
| **Sample Scan** | Сканирование случайной выборки строк | При использовании `TABLESAMPLE` |
| **Subquery Scan** | Сканирование результата подзапроса | Обёртка для подзапроса |
| **Function Scan** | Сканирование результатов функции, возвращающей множество строк | При использовании функций типа `generate_series()` |
| **Values Scan** | Сканирование статического списка значений | При использовании `VALUES` |
| **CTE Scan** | Сканирование результата CTE | При использовании `WITH ... AS` |
| **WorkTable Scan** | Сканирование временной рабочей таблицы | Для рекурсивных CTE |
| **Foreign Scan** | Сканирование внешней таблицы | При использовании FDW (Foreign Data Wrapper) |
| **Custom Scan** | Пользовательское сканирование | Через расширения (например, pg_hint_plan) |

### 🔗 Узлы соединения (Join узлы)

| Узел | Алгоритм | Описание | Когда оптимален |
|------|----------|----------|-----------------|
| **Nested Loop** | Вложенные циклы | Для каждой строки из внешнего набора ищет совпадения во внутреннем | Мало строк во внешнем наборе, есть индекс на внутреннем |
| **Nested Loop Semi** | Вложенные циклы для SEMI JOIN | Как Nested Loop, останавливается после первого совпадения | Для `EXISTS` или `IN` с малым внешним набором |
| **Nested Loop Anti** | Вложенные циклы для ANTI JOIN | Находит строки без совпадений | Для `NOT EXISTS` с малым внешним набором |
| **Hash Join** | Хэш-таблица | Строит хэш-таблицу для меньшего набора, сканирует больший | Большие объёмы данных, нет сортировки |
| **Hash Left Join** | Хэш-таблица для LEFT JOIN | Аналог Hash Join с сохранением всех строк левого набора | Для `LEFT JOIN` на больших таблицах |
| **Hash Semi Join** | Хэш-таблица для SEMI JOIN | Проверяет наличие совпадений через хэш-таблицу | Для `IN`/`EXISTS` на больших объёмах |
| **Hash Anti Join** | Хэш-таблица для ANTI JOIN | Находит строки без совпадений через хэш-таблицу | Для `NOT IN`/`NOT EXISTS` на больших объёмах |
| **Merge Join** | Слияние отсортированных наборов | Сортирует или использует существующий порядок, затем сливает | Данные уже отсортированы, либо есть индексы |
| **Merge Left Join** | Слияние для LEFT JOIN | Аналог Merge Join с сохранением всех строк левого набора | Для `LEFT JOIN` с сортированными данными |

### 📊 Узлы сортировки и агрегации

| Узел | Описание | Особенности |
|------|----------|-------------|
| **Sort** | Явная сортировка строк | Использует внешнюю память при больших объёмах (`external merge disk`) |
| **Incremental Sort** | Инкрементальная сортировка | Сортирует уже частично упорядоченные данные эффективнее |
| **Group** | Группировка строк по ключам (без агрегации) | Промежуточный узел |
| **GroupAggregate** | Группировка с агрегацией через сортировку | Требует сортированных данных |
| **HashAggregate** | Группировка с агрегацией через хэш-таблицу | Не требует сортировки, эффективен при большом количестве групп |
| **Aggregate** | Простая агрегация без группировки | Для `COUNT(*)`, `SUM()`, `AVG()` без `GROUP BY` |
| **WindowAgg** | Вычисление оконных функций | Для `ROW_NUMBER()`, `RANK()`, `LAG()`, `LEAD()` и др. |
| **Unique** | Удаление дубликатов | Обычно после `Sort` для `DISTINCT` |
| **Distinct** | Выбор уникальных значений | Альтернативный способ для `DISTINCT` |

### 📏 Узлы ограничения количества

| Узел | Описание |
|------|----------|
| **Limit** | Ограничение количества возвращаемых строк |
| **Merge Append** | Слияние нескольких отсортированных наборов с ограничением |
| **Recursive Union** | Объединение результатов рекурсивного CTE |

### 🔄 Узлы управления результирующим набором

| Узел | Описание |
|------|----------|
| **Append** | Объединение результатов нескольких дочерних узлов (`UNION ALL`, партиции) |
| **Merge Append** | Объединение отсортированных результатов |
| **Result** | Возврат константного значения или результата выражения |
| **ModifyTable** | Операция модификации данных (`INSERT`, `UPDATE`, `DELETE` на верхнем уровне) |
| **LockRows** | Блокировка строк для `SELECT FOR UPDATE/SHARE` |
| **Materialize** | Материализация подзапроса во временное хранилище (обычно для Nested Loop) |
| **Memoize** | Кэширование результатов подзапроса для повторного использования |
| **SetOp** | Операции над множествами (`INTERSECT`, `EXCEPT`) |

### ⚙️ Узлы оптимизации

| Узел | Описание |
|------|----------|
| **Subquery Scan** | Обёртка для подзапроса для изоляции колонок |
| **InitPlan** | Подзапрос, выполняемый один раз перед основным запросом |
| **Filter** | Остаточная фильтрация строк (применяется после сканирования) |
| **ProjectSet** | Выполнение функций, возвращающих множества (SRF — Set Returning Functions) |
| **BitmapAnd** | Логическое AND для нескольких битовых карт |
| **BitmapOr** | Логическое OR для нескольких битовых карт |

## Ключевые атрибуты узлов

| Атрибут | Формат | Что означает |
|---------|--------|--------------|
| **cost** | `start..total` | Оценочная стоимость (единицы планировщика) |
| **rows** | число | Оценочное количество строк |
| **width** | число (байты) | Средняя ширина строки |
| **actual time** | `start..end` (мс) | Реальное время выполнения узла |
| **actual rows** | число | Реальное количество строк |
| **loops** | число | Количество итераций узла |
| **filter** | условие | Условие фильтрации после сканирования |
| **index cond** | условие | Условие для индексного сканирования |
| **heap blocks** | число | Количество прочитанных страниц таблицы |
| **temp blocks** | число | Количество временных страниц (сортировка/хэш) |

### Атрибуты в выводе BUFFERS

| Атрибут | Описание |
|---------|----------|
| `shared read` | Страницы, прочитанные с диска |
| `shared hit` | Страницы, найденные в кэше |
| `shared dirtied` | Страницы, изменённые в кэше |
| `temp read/written` | Временные страницы для сортировки/хэша |

## Как определить тип узла в плане

```sql
-- Узлы выборки данных: содержит "Scan" в названии
-- Узлы соединения: содержит "Join" в названии
-- Узлы сортировки: Sort, GroupAggregate, HashAggregate
-- Узлы ограничения: Limit, Merge Append
```

### Пример чтения плана

```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM tickets WHERE book_ref = 'TEST02';
```

```
Index Scan using tickets_book_ref_idx on tickets  (cost=0.29..8.31 rows=1 width=...)
   (actual time=0.043..0.044 rows=1 loops=1)
   Index Cond: (book_ref = 'TEST02'::text)
   Buffers: shared hit=3
Planning Time: 0.123 ms
Execution Time: 0.067 ms
```

**Анализ:**
- Используется `Index Scan` — хорошая селективность
- `actual time` очень маленькое — запрос быстрый
- `shared hit=3` — данные найдены в кэше, дисковых чтений не было
- `loops=1` — узел выполнился один раз

### 📚 Полезные команды

```sql
-- Включить логирование всех планов с временем выполнения
LOAD 'auto_explain';
SET auto_explain.log_min_duration = 1000;  -- запросы дольше 1 секунды
SET auto_explain.log_analyze = true;
SET auto_explain.log_buffers = true;
SET auto_explain.log_nested_statements = true;

-- Посмотреть статистику выполнения запросов
SELECT * FROM pg_stat_statements ORDER BY total_time DESC;

-- Сбросить статистику
SELECT pg_stat_statements_reset();
```

## Резюме

`EXPLAIN ANALYZE` — это не просто команда, а **методология** оптимизации. Правильное чтение планов позволяет:

1. Находить узкие места (самые дорогие узлы)
2. Понимать, почему запрос медленный (неправильные оценки, отсутствие индексов)
3. Проверять эффективность созданных индексов
4. Оптимизировать сложные запросы с соединениями и агрегациями

**Золотое правило:** Если вы не смотрели `EXPLAIN ANALYZE` запроса, вы не знаете, как он на самом деле работает.
