System Design: Сервис онлайн-бронирования столиков в ресторанах
Описание задачи
Спроектировать систему для бронирования столиков в ресторанах (аналог OpenTable/Яндекс.Рестораны), которая позволяет пользователям находить и бронировать столики, а рестораны — управлять своими бронированиями.

Функциональные требования
1. Для гостей (клиентов)
Поиск ресторанов:

Поиск по городу, району, метро

Фильтрация: кухня, средний чек, рейтинг, наличие свободных мест

Сортировка: по популярности, рейтингу, близости

Показывать доступные временные слоты (например: 18:00, 18:30, 19:00)

Бронирование:

Выбрать дату, время, количество гостей

Указать особые пожелания (детское кресло, аллергии, день рождения)

Получить подтверждение бронирования (SMS/Email/Push)

Добавить бронь в календарь

Управление бронированиями:

Просмотр активных и прошлых броней

Отмена бронирования (с учётом политики отмены ресторана)

Изменение времени/количества гостей (если ресторан разрешает)

Напоминание за 2 часа до брони

После посещения:

Оставить отзыв и оценку

Загрузить фотографии

Пожаловаться (не пришли, плохое обслуживание)

2. Для ресторанов
Управление столиками:

Настройка схемы зала (столы, их вместимость)

Блокировка столов на ремонт/мероприятия

Установка времени оборачиваемости стола (обычно 1.5-2 часа)

Объединение столов для больших компаний

Управление расписанием:

Часы работы ресторана

Блэкаут даты (закрыто на праздники)

Ограничение бронирований (например, только на ужин по выходным)

Настройка минимального/максимального времени до брони

Обработка броней:

Автоподтверждение или ручное подтверждение

Просмотр всех броней на день/неделю/месяц

Отметка о приходе гостя (checked-in)

Отметка no-show (не пришёл)

Черный список проблемных гостей

Аналитика:

Заполняемость по дням недели/времени суток

Средний процент no-show

Источники бронирований

Популярные временные слоты

3. Системные требования
Нотификации:

SMS/Email/Push при создании/изменении/отмене брони

Напоминание гостю за 2 часа

Уведомление ресторану о новой брони

Алерт при высоком проценте no-show

Антифрод:

Защита от массовых фейковых броней

Лимит на количество активных броней на одного пользователя (не более 5)

Требование депозита для дорогих ресторанов

Система репутации (после 3 no-show — блокировка)

Интеграции:

Экспорт броней в Google Calendar/Outlook

Интеграция с POS-системами ресторанов

Платёжные системы (для депозитов)

Карты (показать маршрут до ресторана)

Нефункциональные требования
1. Performance (производительность)
Масштаб:

10,000 ресторанов в системе

500,000 активных пользователей

50,000 броней в день (~35 броней в минуту)

200,000 RPM (read-heavy: 80% поиск, 20% бронирование)

Latency:

Поиск ресторанов: < 300ms (p95)

Создание брони: < 500ms (p95)

Проверка доступности слотов: < 200ms (p95)

Throughput:

Пиковая нагрузка: пятница/суббота 17:00-19:00 (10x от обычной)

Система должна выдерживать 3000 одновременных бронирований

2. Availability (доступность)
SLA: 99.9% uptime (43 минуты downtime в месяц)

Graceful degradation: если система перегружена, показывать кешированные данные, но блокировать новые брони

Multi-region deployment (Москва, Санкт-Петербург, Казань)

3. Consistency (согласованность)
Strong Consistency для:

Создание/отмена брони (нельзя забронировать один стол дважды)

Списание депозита

Eventual Consistency для:

Обновление рейтинга ресторана

Статистика и аналитика

Синхронизация с внешними календарями

4. Data Retention (хранение данных)
Активные брони: хранить 6 месяцев в основной БД

История броней: архивировать в cold storage (S3) после 2 лет

Отзывы: хранить бесконечно

Логи бронирований: 1 год (для dispute resolution)

5. Security (безопасность)
Аутентификация через OAuth2 (Google/Apple/Phone)

Rate limiting: не более 10 броней с одного IP за час

Защита от SQL injection, XSS

PCI DSS compliance для хранения платёжных данных

GDPR compliance: право на удаление данных

6. Operational Requirements
Monitoring:

Метрики: успешные/неуспешные брони, latency, error rate

Алерты: если процент no-show > 30%, если error rate > 1%

Disaster Recovery:

Ежедневные бэкапы БД

RPO (Recovery Point Objective): 1 час

RTO (Recovery Time Objective): 30 минут

Deployment:

Blue-Green deployment для zero downtime

Feature flags для A/B тестирования новых фич

Canary releases (сначала 5% трафика на новую версию)

Дополнительные челленджи
1. Двойное бронирование (Double Booking)
Проблема: Два пользователя одновременно бронируют последний столик на 19:00.

Как решить?

Optimistic locking с version field

Distributed lock (Redis/Zookeeper)

Reservation timeout (слот блокируется на 5 минут, потом освобождается)

2. Timezone проблемы
Проблема: Пользователь в Москве бронирует ресторан в Владивостоке.

Как решить?

Хранить время в UTC + timezone ресторана

Показывать время в локальной timezone пользователя

Уведомления отправлять в timezone ресторана

3. No-show проблема
Проблема: 30% броней не приходят, ресторан теряет деньги.

Как решить?

Система репутации (score на основе истории)

Требование депозита для популярных ресторанов

Overbooking на основе исторических данных (как в авиакомпаниях)

4. Пиковая нагрузка
Проблема: В пятницу вечером все бронируют рестораны на выходные.

Как решить?

Кеширование доступных слотов (TTL 30 сек)

Queue для обработки броней (RabbitMQ/Kafka)

Rate limiting на уровне пользователя

Что нужно спроектировать
High-Level архитектура: Микросервисы, их взаимодействие, databases

Database schema: Как хранить рестораны, столы, брони, users

API contracts: REST/gRPC endpoints для основных операций

Алгоритм поиска доступных слотов: Как быстро найти свободные столы?

Conflict resolution: Как избежать double booking?

Caching strategy: Что кешировать и на сколько?

Notification system: Как отправлять миллионы SMS/Email без блокировки?

Сложность: Senior-level (требует знания distributed systems, consistency models, caching strategies, и operational concerns)
