# Pricing (ценообразование)

Задача: Спроектировать систему динамического ценообразования для маркетплейса

## Функциональные и нефункциональные требования

Функциональные требования:

1. Базовая функциональность
   - Продавцы выставляют базовую цену товара
   - Система может автоматически изменять цену на основе правил
   - Покупатели видят актуальную цену
   - История цен сохраняется (для аналитики и юридических требований)

2. Правила ценообразования
   - Скидка на определённый период (Black Friday: -30% с 24.11 00:00 до 26.11 23:59)
   - Счастливые часы (каждый день 14:00-16:00 скидка -15%)
   - Сезонные распродажи
3. Услоные правила:
   - Скидка при покупке N штук ("Купи 3, получи скидку 20%")
   - Скидка при покупке на сумму X ("При заказе от 5000₽ скидка 10%")
   - Персональные скидки для VIP клиентов
4. Динамические правила
   - Складской остаток влияет на цену (< 10 штук = +10% к цене, > 1000 штук = -15%)
   - Demand-based pricing (высокий спрос = повышение цены, низкий = понижение)
5. Комбинированные правила
   - Стак правил
   - Есть ограничения на максимальную скидку (не более 70% от базовой цены)
   - Есть минимальная цена (цена закупки + 5%)
6. Юридические требования
   - История изменения всех цен с timestamp и причиной
   - Audit trail: кто и когда изменил правило
   - Защита от price manipulation (нельзя резко менять цену перед акцией)
7. Операционные требования
   - цена не должна прыгать при каждом refresh страницы
   - если цена = 0, должна быть защита от бронирования
   - A/B тестирование правил (для 10% пользователей тестовая цена)

Нефункциональные требования:

1. Perfomance:
   1 млн товаров в каталоге
   100K RPM
   Обновление правил должно применяться ко всем товарам за <5 минут
2. Существующие интеграции
   API для получения цен конкурентов на этот товар (может быть медленным 2-10сек)
   Inventory Service - микросервис склада
   CustomerService - получение VIP статуса клиента
   AnalyticsService - отправка данных о ценовых изменениях

## Важно отменить

Паттерны:

- Стратегия (разные правила = разные стратегии)
- Composite (правила могут комбинироваться)
- Chain Of Responsibility (последовательное применение правил)
- Command (для Audit Trail)
- Memento (для истории цен)

Сервисы:

- Pricing Engine (core)
- Rules Managment (скидки и тд)
- Price History (audit trail)
- Competitor (советы продавцам по снижению цен + платформа для анализа)

Нагрузка:

- кеширование
- предварительная компиляция (read-models)
- Eventual Consistency где возможно

## Основные моменты

1. Нет смысла предкомпилировать цены на товары, поэтому они будут вычисляться on-demand. Правила буду передавать через брокер от сервиса PricingRules до Search. Search будет хранить их в кэше, которые будет инвалидировать

Алгоритм расчета цен:

- Взять товары, подходящие под поисковый запрос
- Получить информацию о клиенте из CustomerService по gRPC: VIP статус, количество покупок, сумма покупок и тд
- Взять все правила образования цен: скидки и тд из кэша (Redis)
- Посчитать цены исходя из информации о пользователе и правилах ценообразования
- Сохранить посчитанные цены в Session Pricing (relation db для сервиса Searcher)

2. Везде где можно используем Eventual Consistency:

- загрузка истории цен
- сравнение цен конкурирующих товаров
- загрузка товаров из Inventory в Search
- передача новых правил от PricingRules до Search

При этом обязательно перед ключевыми действиями нужно проверять состояние master источника данных. Пример: при оформление заказа в OrderService нужно четко понимать, что в InventoryService остался этот товар, для этого синхронно делаем запрос

3. Самые "горящие" места системы нужно предкомпилировать. Пример: в поисковом движке для товаров можно предкомпилировать: история цен, скидка, количество оставшихся товаров, средняя оценка и тд. Благодаря предкомпиляции избавляемся от необходимости делать джойны, ходить во внешние системы и тд, просто читая плоскую read-model. Но ее обязательно нужно инвалидировать асинхронно и делать синхронные проверки перед клювыми действиями: покупка и тд.
