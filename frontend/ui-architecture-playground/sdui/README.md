# Склад — Server-Driven UI (SDUI)

Учебный примерServer-Driven UI. Домен «склад» (товары, категории, цены) придуман только для
того, чтобы показать сам паттерн на живом сценарии.

Главная идея SDUI: **экран — это данные, а не код.** Бэкенд знает не только
бизнес-логику, но и «как выглядит UI»: клиент получает JSON-схему экрана и
просто рисует её. Добавить экран/форму на сервере можно вообще без изменений в
клиенте — контракт тот же, набор элементов тот же.

## Вводная по UI

UI - пользовательский интерфейс, внешний вид и набор графических элементов, с помощью которых человек получает информацию и управляет ей.

UI контрол (элемент управления интерфейсом) - интерактивный компонент программы или сайта, с помощью которого пользователь взаимодействует с системой. 

Графические элементы делятся на типы: элементы ввода, элементы действий, элементы отображений, элементы обратной связи и навигации. Каждый из них несет свою роль

Эта модель покрывает полный цикл взаимодействия «Ввод → Действие → Отображение → Обратная связь» и является стандартом при проектировании дизайн-систем и спецификаций UI-библиотек

### Элементы ввода (input)

Цель контролов: передача данных от пользователя

1. Текстовые поля (input, textarea, search)
2. Числовые и специальные input (number, date, color, file, rating и тд: по факту - прием int, string, date и их вариаций: range, slider)
3. Выбор значения (checkbox, radio, toggle, select, multiselect, combobox)
4. Пошаговый ввод (stepper)
5. Загрузка и редакторы (file upload, rich text editor, code editor)

**Аналогия на бэкенде** - input параметр для функции, request для апи

### Элементы действий (action/command)

Цель контролов: получение иницииативы некоторого процесса, изменения состояния или навигацию

1. Кнопки (primary, secondary, icon, FAB)
2. Ссылки и текстовые кнопки
3. Триггеры форм (submit, reset)
4. Drag and drop зоны (как триггер перемещения)
5. Интерактивные элементы управления состоянием (toggle как действие, а не только ввод)

**Аналогия на бэкенде** - command для сервиса, request для апи

### Элементы отображения (output)

Цель контролов: показать информацию

1. Текст и типографика (heading, labels, paragraphs)
2. Визуальные данные (img, icongs, avatars, charts, maps)
3. Структурированные данные (tables, data grids, lists, trees, masonry)
4. Индикаторы статуса (badges, tags, progress bar, spinner)
5. Контейнеры контента (cards, panels, accordions, tabs content)

**Аналогия на бэкенде** - result из сервиса, response из апи

### Элементы обратной связи и навигации (feedback & navigation)

Цель контролов: управление потоком пользователя и сообщение о результатах действий/событий

1. Навигация (menu, sidebar, breadcrumbs, pagination, tabs header)
2. Модальные окна и диалоги (modal, dialog, confirmation)
3. Уведомления (toast, snackbar, alert, banner)
4. Подсказки (tooltip, popover, helper text)
5. Пустые состояния и ошибки (empty state, validation message)

### Логика SDUI и как заставить бэкенд отвечать за фронтенд

Каждый UI контрол имеет: внешний вид (обычно привычный ui-kit); взаимодействия, которые можно с ним совершить (нажать, заполнить); результат взаимодействия с ним: перерендер/открытие страницы/элемента (mutations/replaces), тоаст, перенавигация; данные, с помощью которых он рендерится (text - текст, button - название, grid - данные)

Собственно это все данные, которые нужны для любого контрола. Контролы можно комбинировать, вкладывать один в другой и тд, тем самым собирать множество вариаций

Надо разделить для SDUI две разные задачи: как показать конкретный контрол, взаимодействия с ним и feedback от его работы; как показать целую страницу в виде вариаций контролов (grid, flex)

То есть бэкенд для SDUI должен уметь под каждый контрол предоставить данные + предоставить данные для того, как рисовать конкретные экраны (расположение элементов на странице)

## Контракт SDUI

Зеркалится один в один: `backend/Sdui.Api/Sdui/Contract.cs` ↔
`frontend/src/contract.ts`.

| Концепция | Как выглядит в JSON |
|-----------|---------------------|
| **Экран** | `{ view, title, hint, actions[], sections[] }` |
| **Элементы** | `banner`, `chips`, `list`, `card`, `actions`, `form` — дискриминатор `kind` |
| **Действия** | `navigate` (screen+query), `back`, `refresh`, `delete` (entity+id+confirm), `apply` (инлайн-мутация), `reset` |
| **Поле формы** | `text`, `textarea`, `number`, `select`, `switch`, `date` + `value` + `rules` |
| **Ответ мутации** | `{ ok, toast, next }` или `{ ok:false, errors: {поле: текст} }` |

Ключевое: **клик не зашит в клиенте.** И у чипа, и у строки списка, и у кнопки
есть собственное `action`, присланное сервером. Клиент не знает, что категория —
это query-параметр: он просто исполняет `navigate`. Поэтому же клиент не знает
имена экранов `product`/`catalog`/`search` — только конечную таблицу
screen→url в `api.ts`.

## Режим дизайнера (Grafana-like)

Отдельная страница «🛠 Редактор» (плавающая кнопка справа сверху): перетаскиваете
панели — и **витрина рендерится по вашей раскладке**, без изменений кода и
передеплоя. Это сама суть SDUI: вид экрана — данные, а не код.

- Раскладка хранится на сервере (`LayoutStore`), эндпоинты
  `GET/PUT /api/layout/{catalog|product}`, `POST …/restore`, `GET /api/layout/meta`.
- Палитра в дизайнере строится из `meta`-описания с сервера: **клиент не знает
  имён панелей** — «Фильтр», «Список позиций», «Карточка сводки» для каталога;
  «Карточка атрибутов», «Инлайн-остаток», «Действия» для карточки товара.
- Панель — это `LayoutItem{ kind, width, props }`; реордер — нативный HTML5 DnD
  (dragstart/drop несут индекс в `dataTransfer`, без библиотек).
- **Панели можно ставить РЯДОМ**: у каждой есть ширина в 12-колоночной сетке
  (кнопки `1/1 · 1/2 · 1/3`), сервер сам укладывает соседей в один `grid`-элемент
  с `span` (см. `Assemble` в `SduiBuilder.cs`). Одиночная панель на строке —
  обычная секция, без обёртки.
- Кнопки шапки тоже из раскладки: включаются/выключаются чекбоксом, текст
  редактируется, порядок — стрелками.
- Панели-виджеты умеют **внутренние настройки**: чекбоксы «Показывать
  цены/теги/хвост», «Лимит строк» для списка; «Категория/Поставщик/Акция/…» для
  карточки товара; «Кнопка −1/+1/списать» для инлайн-остатка; галочки для
  Действий (Изменить/Удалить). Плюс **текстовые пропы**: заголовок чипов
  фильтра/сортировки, шаблон подзаголовка строк, свой текст баннера
  (`{count}` подставляется сервером), поля карточки сводки.
- Сброс `/api/runtime/reset` возвращает и товары, и раскладки к сиду — e2e
  остаётся идемпотентным, дефолтные раскладки в точности повторяют прежний вид.

Благодаря этому «добавить панель» = серверный виджет превращается в элемент
схемы тем же путём, что и всегда: `ResolveCatalog/ResolveProduct` собирают
`Element`'ы в `sections` в порядке из раскладки.

## Экраны и «сколько можно навертеть»

Клиент не менялся под каждый новый экран — добавились только **данные на
бэкенде** (ну и два новых типа действия):

- **dashboard** — баннер, чипы быстрого перехода, сводка «стоимость склада»;
- **catalog** — фильтр-чипы, **чипы сортировки** (цена/остаток/новизна),
  поиск `q`+`by`, чип «Сбросить», валюта из настроек, тег «акция»;
- **product** — карточка со всеми атрибутами + **кнопки инлайн-мутаций**
  «−1 / +1 / Списать весь остаток» (действие `apply`, без формы);
- **form-product** — все виды полей: text, select (категория, поставщик),
  number с единицей, date, switch×2, textarea;
- **categories** + **form-category** — создать категорию формой, она сразу
  чипом появляется в каталоге (без изменений фронтенда);
- **search** — select «по какому полю» + запрос, результат открывается фильтром каталога;
- **stats** — считает сервер и отдаёт строки;
- **settings** — валюта и показ неактивных: **влияют на каталог сразу**,
  ни одного изменения на клиенте.

Тот же DOM-слой, что раньше: `toggle-показ неактивных` выключил — каталог
стал короче; `валюта $` — цены в каталоге, карточке и статистике в долларах.

## Как сценарий ложится на паттерн

| Шаг (e2e) | Кто решает |
|-----------|-----------|
| 1–2. Каталог + фильтр по категории | сервер сам собирает чипы, счётчики и query для `navigate` |
| 3. Детали товара | сервер отправляет `card`-поля (ценит и «нет в наличии» сам) |
| 4. Префилл формы | сервер вкладывает `value` в поля схемы |
| 5. Ошибки валидации | локальная копия `rules` — лишь подсказка; **арбитр — сервер** (его `errors` перезаписывают) |
| 6–7. Сохранение/создание | сервер возвращает `{ ok, toast, next }` — «куда идти» решает он |
| 8. Удаление | подтверждение с текстом из схемы; `next` после мутации — от сервера |
| 9. JSON-схема + reload | вкладка «Показать JSON-схему экрана» показывает сырые данные экрана |

## Ключевые решения

1. **Рендерер — один `switch`** (`elements.tsx`). Неизвестный `kind` — не
   падение, а баннер «клиент старше сервера» (жёсткая деградация).
2. **Мутации идут через runtime-эндпоинты** (`/api/runtime/submit`,
   `/api/runtime/delete`, `/api/runtime/apply`, `/api/runtime/reset`), а не
   REST-ресурсы: клиент всё равно работает со схемами, а не с доменом.
3. **Форма без библиотек**: `useRef` на поля, сборка значений по `name`,
   локальные правила из схемы (не блокируют отправку!). Управляемые поля не
   нужны — форма «спрашивает» у сервера.
4. **Навигация без роутера**: стек истории в `use-screen.ts`,
   `back` приходит действием, `refresh` перезапрашивает текущий экран.
5. **Диалоги и тосты** — промис-подход с `useSyncExternalStore`: тот же паттерн,
   что и promise-диалоги у канбан-версий.
6. **Данные e2e-идемпотентны**: `POST /api/runtime/reset` (откат к сиду)
   вызывается в начале `e2e/sdui-e2e.cjs`.
7. **UI-состояние тоже серверное**: валюта, «показ неактивных», добавленные
   категории живут в `Store`, а reset с фактическим `store.Reset()`
   возвращает `{ ok, toast, next }` — как любая мутация.
8. **Каталог и карточка товара собираются из раскладки** (`SduiBuilder.Catalog`,
   `SduiBuilder.Product`): дефолтная раскладка = прежний вид 1-в-1, пользовательская
   приходит из «🛠 Редактора». «Добавить экран на клиенте» не требуется даже тут.
9. **Один `ScreenView`** (`screen-view.tsx`) рендерит и витрину, и живое превью
   в дизайнере — превью это ровно тот же клиентский рендерер схем.


## Запуск

```
backend/  ASP.NET Core (net9) minimal API — владелец UX и бизнес-логики
frontend/ React 19 + TypeScript + Vite — «тонкий» рендерер схем
```

```bash
# терминал 1 — бэкенд
cd sdui/backend/Sdui.Api && dotnet run        # http://localhost:7120

# терминал 2 — фронтенд
cd sdui/frontend && npm install && npm run dev # http://localhost:5210
```

Vite-прокси шлёт `/api/*` на `7120`, поэтому CORS не нужен и клиент ходит
same-origin.

```bash
cd sdui/frontend
npm run build    # typecheck (tsc --noEmit) + vite build
npm run e2e      # 9-шаговый сценарий (нужны оба сервера)
```
