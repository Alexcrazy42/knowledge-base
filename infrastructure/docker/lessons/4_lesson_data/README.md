# Docker — Урок 4. Данные: volumes, bind mounts, tmpfs, backup/restore

Здесь — про то, **где жить данным**, когда контейнер умирает, и как **не потерять** базу.

---

## 4.1 Проблема: writable layer умирает вместе с контейнером

По умолчанию **все файлы**, созданные внутри контейнера, лежат в **writable layer** — тонком слое **поверх** read-only слоёв образа.

```
┌─────────────────────────────┐
│  Writable layer (RW)        │  ← всё, что создаёт контейнер
├─────────────────────────────┤
│  Image layer N (RO)         │
│  ...                        │
│  Image layer 1 (RO)         │
└─────────────────────────────┘
```

**Ключевые свойства writable layer:**

1. **Уникален для каждого контейнера.** Не шарится между контейнерами.
2. **Умирает при `docker rm`.** Данные **не восстановить**.
3. **Его трудно «вынуть»** на хост или передать другому контейнеру.
4. **`docker commit` — не бэкап.** Превратить контейнер в образ можно, но это **не** стратегия резервного копирования.

**Вывод:** всё, что должно **пережить** контейнер (база, загрузки, сертификаты), должно лежать **вне** writable layer. Docker даёт **три** механизма для этого.

---

## 4.2 Три механизма: обзор

| | **Named volume** | **Bind mount** | **tmpfs** |
|---|---|---|---|
| **Кто управляет** | Docker daemon | Вы (путь на хосте) | Ядро (RAM) |
| **Где лежит** | `/var/lib/docker/volumes/<name>/_data` | Любой путь хоста | В памяти хоста |
| **Переживает `docker rm`?** | ✅ **Да** | ✅ Да (это папка хоста) | ❌ **Нет** |
| **Переживает reboot?** | ✅ Да | ✅ Да | ❌ **Нет** |
| **Шарится между контейнерами?** | ✅ Да | ✅ Да | ❌ **Нет** |
| **Для production?** | ✅ **Рекомендуется** | ⚠️ Осторожно | ❌ Только временное |
| **Типичное использование** | Базы, state | Код в dev, конфиги | Секреты, кэш, temp |

**Мнемоника:**

- **volume** — «диск, которым управляет Docker» (для прода);
- **bind mount** — «папка хоста, которую видит контейнер» (для dev);
- **tmpfs** — «оперативка, которая исчезает» (для секретов и кэша).

## 4.3 Named volumes: рекомендуемый способ для production

### 4.3.1 Что это

**Named volume** — это **хранилище, полностью управляемое Docker daemon**. Вы ссылаетесь на него **по имени**, а Docker решает, **где** его положить (по умолчанию `/var/lib/docker/volumes/<name>/_data`).

```bash
docker volume create mydata
docker run -d --name db -v mydata:/var/lib/postgresql/data postgres:16
```

**Что происходит:**

- Docker создаёт каталог `/var/lib/docker/volumes/mydata/_data`;
- монтирует его в `/var/lib/postgresql/data` контейнера;
- данные **переживают** `docker rm db` (пока не удалён сам volume);
- данные **переживают** reboot хоста.

### 4.3.2 Почему это «правильный» способ

1. **Переносимость.** Volume **не привязан** к структуре каталогов хоста. `compose up` на любом Linux-хосте с Docker даст **тот же** результат, без необходимости создавать конкретные пути.

2. **Инициализация из образа.** Если volume **пуст** при первом старте, Docker **копирует** содержимое соответствующего каталога из образа в volume. Для PostgreSQL это значит, что `/var/lib/postgresql/data` **инициализируется корректно**.

   > ⚠️ **Критично:** с bind mount на **пустую** папку хоста — всё наоборот: пустая папка **перезаписывает** содержимое образа, и база **падает** при старте. Это ловушка, на которую попадаются почти все.

3. **Драйверы.** Volume может быть «за» плагином (NFS, cloud block storage), и вы просто ссылаетесь на имя — остальное делает драйвер.

4. **Безопасность.** Docker **не даёт** контейнеру напрямую писать в произвольные места хоста — только в volume, который вы явно смонтировали.

### 4.3.3 Named vs anonymous volumes

| | **Named** | **Anonymous** |
|---|---|---|
| **Имя** | `mydata` | случайный хэш |
| **Как создать** | `-v mydata:/data` | `-v /data` (без имени) |
| **Управление** | Легко: по имени | Трудно: нужно найти хэш |
| **Для production** | ✅ | ❌ |

**Правило:** всегда **давайте имя** volume. Анонимные volume — только если Docker сам создаёт их через `VOLUME` в Dockerfile, и вы **точно** знаете, что делаете.

### 4.3.4 `-v` vs `--mount`

Docker поддерживает **два синтаксиса**:

```bash
# Короткий (-v)
docker run -v mydata:/data ...

# Длинный (--mount) — рекомендуется в документации
docker run --mount type=volume,source=mydata,target=/data ...
```

**Рекомендуется `--mount`**: он **явный** (тип, источник, цель), и в нём **сложнее** случайно сделать опечатку, которая создаст не тот mount. `-v` короче, но менее читаем.

### 4.3.5 Управление volumes

```bash
docker volume ls                    # список
docker volume inspect mydata        # где лежит, драйвер, mountpoint
docker volume rm mydata             # удалить (только если не используется)
docker volume prune                 # удалить все неиспользуемые (ОСТОРОЖНО)
```

**Важно:** `docker volume prune` **удаляет данные**. Никогда не запускайте на проде без понимания, какие volume не используются **сейчас** (но могут быть нужны **позже**).

## 4.4 Bind mounts: прямая связь с хостом

### 4.4.1 Что это

**Bind mount** создаёт **прямую связь** между **путём на хосте** и **путём в контейнере**. Docker **не управляет** этим каталогом — он просто «пробрасывает» его.

```bash
docker run -v /home/user/app:/app myapp
# или
docker run --mount type=bind,source=/home/user/app,target=/app myapp
```

**Что происходит:**

- каталог `/home/user/app` на хосте виден как `/app` в контейнере;
- изменения **на хосте** сразу видны **в контейнере** (и наоборот);
- Docker **не** создаёт каталог, если его нет (в `--mount` — ошибка; в `-v` — Docker **создаст** каталог, что может быть сюрпризом).

### 4.4.2 Плюсы и минусы

**Плюсы:**

- **Live-reload в разработке:** меняете код на хосте → сразу видите в контейнере;
- **Прямой доступ к логам/конфигам** с хоста;
- **Никакой «магии»** — вы точно знаете, где лежат данные.

**Минусы:**

- **Привязка к пути хоста.** `compose up` на другой машине может не сработать, если пути другие.
- **Права.** UID/GID на хосте и в контейнере могут не совпадать → `Permission denied` — **классическая** боль.
- **Безопасность.** Контейнер может **писать в любое место** на хосте, которое вы смонтировали (включая symlink-выход за пределы каталога).
- **Производительность на macOS/Windows.** Bind mount **пересекает границу VM** (Docker Desktop) → **значительно медленнее**, чем volume, особенно на интенсивном I/O.

### 4.4.3 Когда использовать

- **Разработка:** код, конфиги, live-reload.
- **Инъекция конфигов** (например, `nginx.conf` с хоста).
- **Логи** — если хотите видеть их напрямую на хосте.

**Когда не использовать:**

- **Production-данные** (базы, uploads) → **named volume**.
- **Секреты** → **tmpfs** или secret mount (урок 2).
- **macOS/Windows** для интенсивного I/O → **named volume** быстрее.

### 4.4.4 Read-only bind mount

```bash
docker run --mount type=bind,source=/host/config,target=/etc/app,readonly myapp
# или
docker run -v /host/config:/etc/app:ro myapp
```

**Зачем:** контейнер **не может** изменить файл на хосте. Полезно для конфигов, сертификатов, «только для чтения» данных.

## 4.5 tmpfs: данные только в памяти

### 4.5.1 Что это

**tmpfs mount** хранит файлы **в оперативной памяти хоста**, **никогда** не записывая их на диск.

```bash
docker run --mount type=tmpfs,destination=/app/cache myapp
# или
docker run --tmpfs /app/cache myapp
```

**Ключевые свойства:**

- **Не переживает остановку контейнера** — данные **исчезают** при `stop` / `rm`;
- **Не переживает reboot хоста**;
- **Не шарится** между контейнерами;
- **Считается в memory limit** контейнера (`--memory`): заполнение tmpfs может привести к **OOM**.

### 4.5.2 Когда использовать

| Сценарий | Почему tmpfs |
|---|---|
| **Секреты в runtime** (токены, пароли, расшифрованные ключи) | Не попадают на диск → нет риска утечки через файловую систему |
| **Кэш / scratch space** для интенсивных вычислений | Быстрее диска, автоматически чистится |
| **PID-файлы, сокеты** | Не нужно хранить, не должно оставаться после контейнера |
| **Временные файлы БД** (sort, temp) | Ускоряет, не засоряет диск |
| **Malware scanning** | Файлы не оседают на диске |

### 4.5.3 Ограничения

- **Только Linux.** На Windows/macOS (Docker Desktop) tmpfs работает **внутри Linux VM**, но не даёт «настоящей» памяти хоста Windows.
- **Считается в memory limit.** `size=` **не** даёт дополнительной RAM сверх `--memory`.
- **Не шарится** между контейнерами.
- **Может уйти в swap.** Если swap включён, «память» tmpfs может быть выгружена на диск — это **подрывает** идею «только RAM».

### 4.5.4 `--tmpfs` vs `--mount type=tmpfs`

| | **`--tmpfs`** | **`--mount type=tmpfs`** |
|---|---|---|
| **Синтаксис** | Короткий | Явный |
| **Гибкость опций** | Больше (можно `size=`, `mode=`) | Чуть меньше |
| **Swarm** | ❌ Нельзя | ✅ Можно |

**Рекомендация:** для compose / swarm — **`--mount`**; для быстрых `docker run` — `--tmpfs` допустим.

## 4.6 Сравнительная таблица: что когда использовать

| Задача | **Volume** | **Bind mount** | **tmpfs** |
|---|---|---|---|
| База данных в production | ✅ **Да** | ❌ Нет (права, инициализация) | ❌ Нет |
| Код в dev с live-reload | ❌ Нет (stale) | ✅ **Да** | ❌ Нет |
| Конфиг nginx с хоста | ⚠️ Можно (через `docker cp`) | ✅ **Да** (read-only) | ❌ Нет |
| Секреты в runtime | ⚠️ Только через secret mount | ❌ Нет (на диске) | ✅ **Да** |
| Кэш / temp | ⚠️ Можно, но останется | ❌ Нет | ✅ **Да** |
| Uploads пользователей | ✅ **Да** | ⚠️ Осторожно (права) | ❌ Нет |
| Логи, которые хочет видеть хост | ⚠️ Через `docker logs` | ✅ **Да** | ❌ Нет |
| macOS/Windows, интенсивный I/O | ✅ **Да** (быстрее) | ❌ Медленно | ✅ (в VM) |

**Мнемоника:**

> **Volume** — «Docker владеет» (prod).
> **Bind** — «хост владеет» (dev).
> **tmpfs** — «память владеет» (секреты, temp).

## 4.7 Backup/restore: как **не потерять** volume

### 4.7.1 Главный принцип

**Volume persistence ≠ backup.** Volume переживает контейнер, но **не** переживёт:

- `docker volume rm`;
- `docker volume prune`;
- потерю диска;
- ошибку в приложении, которая **испортит** данные.

**Бэкап — обязателен** для всего, что нельзя восстановить из образа или кода.

### 4.7.2 «Универсальный» метод: tar через временный контейнер

Самый **переносимый** способ — смонтировать volume в **временный** контейнер и **заархивировать** его.

**Backup:**

```bash
# 1. (Рекомендуется) остановить приложение для консистентности
docker stop myapp

# 2. Запустить временный alpine, смонтировать volume readonly + каталог для бэкапа
docker run --rm \
  -v mydata:/source:ro \
  -v $(pwd)/backups:/backup \
  alpine tar czf /backup/mydata-$(date +%Y%m%d-%H%M%S).tar.gz -C /source .

# 3. Запустить приложение обратно
docker start myapp
```

**Почему `:ro` (read-only):** гарантирует, что бэкап **не изменит** данные. Для консистентности — **лучше** остановить контейнер (или использовать «заморозку» / snapshot на уровне ФС).

**Restore:**

```bash
# 1. Остановить приложение
docker stop myapp

# 2. (Опционально) очистить volume для «чистого» восстановления
docker run --rm -v mydata:/target alpine sh -c "rm -rf /target/*"

# 3. Распаковать архив
docker run --rm \
  -v mydata:/target \
  -v $(pwd)/backups:/backup:ro \
  alpine tar xzf /backup/mydata-20250101-120000.tar.gz -C /target

# 4. Запустить приложение
docker start myapp
```

**Важно:** `tar` **сохраняет** UID/GID и права — это обычно **то, что нужно** для баз данных и приложений с фиксированным пользователем.

### 4.7.3 Альтернативы

| Метод | Плюсы | Минусы |
|---|---|---|
| **`tar` через временный контейнер** | Универсальный, не зависит от ФС, легко автоматизировать | Медленнее для больших объёмов |
| **`rsync` напрямую из `/var/lib/docker/volumes/.../_data`** | Быстро, инкрементально | **Не рекомендуется** Docker (прямой доступ к volume — undefined behavior); может сломать данные |
| **Restic / Borg** | Дедупликация, шифрование, инкрементальность | Нужна настройка, внешнее ПО |
| **Snapshot на уровне ФС** (LVM, ZFS, Btrfs) | Мгновенно, консистентно | Требует поддержки ФС на хосте |
| **Остановка стека + `tar`** | Максимальная консистентность | Downtime |

**Правило:** для **маленьких** volume — `tar`; для **больших** — snapshot ФС или restic/borg; для **баз** — **сначала** логический дамп (`pg_dump`), **потом** файловый бэкап (или и то, и другое).

### 4.7.4 Бэкап **баз данных** — особый случай

**Файловый бэкап работающей БД может быть неконсистентным.** PostgreSQL/MySQL пишут в несколько файлов, и `tar` в произвольный момент может поймать **полусостояние**.

**Правильные стратегии:**

1. **Логический дамп:** `pg_dump` / `mysqldump` — **всегда** консистентен, но медленный и не «полный» (не включает некоторые системные вещи).
2. **Остановка + `tar`:** консистентно, но downtime.
3. **Snapshot ФС + `tar`:** консистентно, без downtime (если ФС поддерживает).
4. **Непрерывный архив WAL / binlog** — для point-in-time recovery (PITR).

**Минимум для прода:** **ежедневный** логический дамп + **еженедельный** файловый/снэпшот-бэкап.

### 4.7.5 Автоматизация и проверка

**Скрипт бэкапа** должен:

- делать **временную метку** (`$(date +%Y%m%d-%H%M%S)`);
- **проверять** успех (`set -e` + `sha256sum`);
- **ротировать** старые бэкапы (хранить N последних);
- **логировать**, куда положен файл и его размер.

**И главное:** **проверяйте restore.** Бэкап, который **никогда не восстанавливали**, — это **не бэкап**, а надежда. Раз в квартал — **разворачивайте** бэкап в тестовое окружение и **проверяйте**, что данные на месте.

## 4.8 Типичные ошибки и подводные камни

### 4.8.1 Bind mount на пустую папку «затирает» образ

**Симптом:** PostgreSQL с bind mount на пустой каталог хоста **падает** при старте.

**Причина:** Docker **не** копирует содержимое образа в bind mount. Пустая папка **перекрывает** `/var/lib/postgresql/data` из образа.

**Решение:** для баз — **named volume** (он **инициализируется** из образа при первом старте).

### 4.8.2 `Permission denied` на bind mount

**Симптом:** контейнер не может писать в смонтированный каталог.

**Причина:** UID/GID процесса в контейнере **не совпадает** с владельцем файлов на хосте.

**Решения:**

- запускать контейнер с `--user $(id -u):$(id -g)`;
- `chown` каталога на хосте под нужного пользователя;
- использовать **named volume** (Docker сам управляет правами).

### 4.8.3 `docker volume prune` удалил «нужные» данные

**Симптом:** после `prune` пропали volume, которые **не были** подключены **сейчас** (но были нужны **потом**).

**Причина:** `prune` удаляет **все** volume, **не подключённые** ни к одному **запущенному** контейнеру.

**Решение:** **никогда** не запускать `prune` на проде без `--filter` (например, `--filter label!=keep`) и без понимания, **что** будет удалено.

### 4.8.4 macOS/Windows: bind mount «тормозит»

**Симптом:** интенсивный I/O (например, `node_modules`) в bind mount на Docker Desktop **очень медленный**.

**Причина:** bind mount **пересекает границу VM** (Linux VM ↔ Windows/macOS), что даёт **огромный** overhead.

**Решение:** для `node_modules` и подобного — **named volume** (или `volume` + `-v` для исключения). На **Linux** разница минимальна.

### 4.8.5 tmpfs «съел» всю память и вызвал OOM

**Симптом:** контейнер с `--tmpfs` и большим `size=` падает по OOM, хотя `--memory` задан.

**Причина:** tmpfs **считается** в memory limit контейнера, и `size=` **не** даёт RAM **сверх** лимита.

**Решение:** либо уменьшить `size=`, либо увеличить `--memory`, либо использовать **disk-based** storage, если данные **не** должны быть в RAM.

## 4.9 Шпаргалка: что использовать в каком случае

| Задача | Инструмент |
|---|---|
| База данных в **production** | **Named volume** |
| Код в **dev** с live-reload | **Bind mount** |
| Конфиг **только для чтения** | **Bind mount `:ro`** |
| **Секреты** в runtime | **tmpfs** (или secret mount, урок 2) |
| **Кэш / temp** | **tmpfs** |
| **Uploads** пользователей | **Named volume** |
| **Логи**, которые хочет видеть хост | **Bind mount** (или log driver) |
| **Бэкап** volume | **`tar`** через временный контейнер |
| **Бэкап** БД | **Логический дамп** + файловый бэкап |
| Проверить volume | `docker volume inspect` |
| Очистить **неиспользуемые** volume | `docker volume prune` (**осторожно!**) |

## Вопросы контрольные

**1. Почему `docker commit` нельзя считать стратегией бэкапа?**

Ответ: `docker commit` создаёт **образ** из writable layer контейнера. Но: (а) он **не** включает volume и bind mounts — то есть **все** persistent-данные остаются **снаружи**; (б) writable layer **не предназначен** для хранения данных — его производительность ниже, чем у volume; (в) образ — **иммутабельный** артефакт, а не «снимок живой системы»; (г) коммит **не** гарантирует консистентность (процесс продолжает писать во время коммита). Для бэкапа данных нужен **бэкап volume** (tar / restic / логический дамп) и **восстановление** через монтирование, а не через `docker commit`.

**2. Ты запускаешь PostgreSQL с `-v /home/user/pgdata:/var/lib/postgresql/data`, папка `/home/user/pgdata` пустая. Контейнер падает. Почему? Что изменить?**

Ответ: **bind mount** на **пустую** папку **перекрывает** содержимое образа. В образе `postgres` в `/var/lib/postgresql/data` есть **начальные файлы** (шаблоны, конфиги, `PG_VERSION`). Пустая папка хоста **скрывает** их, и PostgreSQL **не может** инициализироваться → падение. Решение: использовать **named volume** (`-v pgdata:/var/lib/postgresql/data`) — Docker **скопирует** содержимое из образа в volume при **первом** старте, и база инициализируется корректно.

**3. В чём разница между `-v mydata:/data` и `-v /host/path:/data` с точки зрения «кто владеет» и «что переживёт `docker rm`»?**

Ответ: `-v mydata:/data` — **named volume**: им **управляет Docker**, он лежит в `/var/lib/docker/volumes/mydata/_data`, **переживает** `docker rm` (пока не удалён сам volume), **инициализируется** из образа при первом старте, и **не привязан** к пути хоста. `-v /host/path:/data` — **bind mount**: им **управляете вы** (путь хоста), Docker **не** создаёт и **не** инициализирует его, данные **переживают** `docker rm` (это просто папка хоста), но **привязаны** к конкретному пути и **подвержены** проблемам с правами и «затиранию» образа. Для **production-данных** — volume; для **dev-кода/конфигов** — bind mount.

**4. Почему tmpfs не подходит для хранения данных, которые должны пережить остановку контейнера? И в чём подвох с `size=` и `--memory`?**

Ответ: tmpfs хранит данные **только в RAM** хоста и **удаляет** их при остановке контейнера (и при reboot). Это **by design** — tmpfs для **временных** данных. Подвох с `size=` и `--memory`: tmpfs **считается** в memory cgroup контейнера. Если задан `--memory=256m` и `--tmpfs /data:size=512m`, это **не** значит, что контейнер получит 512 МБ **сверх** 256 МБ. **Заполнение** tmpfs **сверх** `--memory` приведёт к **OOM kill** контейнера. `size=` ограничивает **размер** tmpfs, но **не** расширяет memory limit.

**5. Как правильно сделать бэкап named volume `pgdata`, который используется PostgreSQL, и почему нельзя просто `tar` запущенного каталога?**

Ответ: **Нельзя** просто `tar` запущенного каталога, потому что PostgreSQL **пишет** в несколько файлов, и `tar` в произвольный момент может поймать **неконсистентное** состояние (например, страницу данных, которая ещё не сброшена на диск, или половину транзакции). Правильно: (а) **логический дамп** (`pg_dump`) — всегда консистентен; (б) **остановить** контейнер → `tar` через временный контейнер (`-v pgdata:/source:ro -v $(pwd)/backups:/backup alpine tar czf ...`) → **запустить** контейнер; (в) **snapshot ФС** (LVM/ZFS/Btrfs) + `tar` — без downtime, если ФС поддерживает. **Минимум для прода:** ежедневный `pg_dump` + еженедельный файловый/снэпшот-бэкап, и **регулярная проверка restore**.

**6. Почему на macOS bind mount «тормозит», а на Linux — нет? Что использовать вместо?**

Ответ: на **Linux** bind mount и volume работают **нативно** (это просто каталоги в той же ФС), разница **минимальна**. На **macOS/Windows** (Docker Desktop) контейнеры работают **внутри Linux VM**, и bind mount **пересекает границу VM** (virtiofs/9p), что даёт **значительный** overhead на интенсивном I/O (например, `node_modules`, сборки). **Решение:** для тяжёлых каталогов (`node_modules`, `.venv`, `target`) — **named volume** вместо bind mount (данные останутся «внутри» VM, без пересечения границы). Для кода — bind mount всё равно нужен для live-reload, но тяжёлые артефакты — в volume.

**7. Чем `--mount` лучше `-v`? Приведи два конкретных сценария, где разница критична.**

Ответ: `--mount` **явный** (тип, источник, цель) и **менее подвержен** опечаткам, которые создают **не тот** mount. Два критичных сценария: (а) **bind mount на несуществующий путь**: `-v /host/nonexistent:/data` **создаст** каталог на хосте (часто не то, что хотели), а `--mount type=bind,...` **упадёт** с ошибкой — что **лучше** (вы узнаете о проблеме сразу); (б) **tmpfs с опциями**: `--mount` поддерживает **все** опции в явном виде, а `--tmpfs` — ограничен, и **нельзя** использовать в Swarm-сервисах (только `--mount`). Плюс `--mount` **читаемее** в compose-файлах, где важна ясность.
