## 3.1 Базовая модель: что видит контейнер

Контейнер **не знает**, к какой сети он подключён и кто его соседи. Он видит только **сетевой интерфейс**, **IP-адрес**, **шлюз**, **таблицу маршрутизации** и **DNS-сервис** — как обычный Linux-хост. Всё остальное — работа Docker и ядра хоста.

Упрощённо:

```
┌──────────────────────────────────────────────────┐
│  Контейнер                                       │  ← это NET namespace
│  ┌────────────┐   ┌───────────────────────────┐  │
│  │ eth0       │──▶│ /etc/resolv.conf         │  │
│  │ 172.17.0.2 │   │ nameserver 127.0.0.11     │  │
│  └────────────┘   └───────────────────────────┘  │
│         │                                        │
│         ▼                                        │
│  ┌─────────────────────────────────────────────┐ │
│  │  Ядро хоста: namespaces, iptables, veth     │ │  ← ЭТОГО контейнер не видит
│  └─────────────────────────────────────────────┘ │
└──────────────────────────────────────────────────┘
```

**Ключевой принцип:** сеть в Docker — это **драйвер**, который решает, **как** создать этот интерфейс, **какой** IP дать и **как** маршрутизировать пакеты. Драйверов несколько, и у каждого своя зона ответственности.

eth0 с IP 172.17.0.2

Это внутри контейнера. А на хосте у этого же «соединения» есть второй конец — veth-интерфейс:

```
Хост (namespace хоста)                        Контейнер (NET namespace)
─────────────────────────                     ──────────────────────────
veth3f2a9c1  ──────(veth-пара)──────▶  eth0
    │                                    │
    │                                    └─ 172.17.0.2
    └─ подключён к docker0 (172.17.0.1)
```

veth-пара — это как труба: что входит с одного конца, выходит с другого. Один конец — на хосте (и подключён к bridge), другой — в контейнере (и выглядит как eth0).

Контейнер не знает, что его eth0 — это половина трубы. Для него это просто «сетевуха».

127.0.0.11 в /etc/resolv.conf

Это Docker embedded DNS — специальный адрес, по которому Docker запускает встроенный DNS-сервер внутри каждого контейнера в пользовательской сети.

Важно: это не «настоящий» DNS-сервер на 127.0.0.11. Docker перехватывает запросы к 127.0.0.11:53 через iptables в NET namespace контейнера и направляет их в свой процесс dockerd. Поэтому:

- ping db → запрос идёт на 127.0.0.11 → Docker отвечает 172.18.0.3;
- ping google.com → запрос идёт на 127.0.0.11 → Docker не знает такого имени → форвардит на upstream DNS хоста.

Важный нюанс: в дефолтном docker0 этого DNS нет. Там 127.0.0.11 не появится, и ping db по имени не сработает (см. Lab 1A). Это фича только user-defined сетей.

## Что реально происходит при docker run --network my-net alpine sleep 1000

- dockerd видит --network my-net → ищет сеть my-net (драйвер bridge).
- dockerd создаёт NET namespace для контейнера (через runc).
- dockerd создаёт veth-пару: один конец — в namespace контейнера (станет eth0), второй — в namespace хоста (подключится к bridge br-<hash> для my-net).
- dockerd назначает IP из подсети my-net (например, 172.18.0.2), настраивает маршрут по умолчанию через шлюз 172.18.0.1 (это IP самого bridge’а на хосте).
- dockerd прописывает /etc/resolv.conf с 127.0.0.11 (потому что my-net — user-defined).
- dockerd добавляет iptables-правила в NET namespace контейнера: «запросы к 127.0.0.11:53 → перехватить и отдать в dockerd».
- runc делает clone() с флагом CLONE_NEWNET (новый NET namespace), pivot_root, execve("sleep", ["1000"]).
- Контейнер запущен. sleep видит только lo и eth0 с 172.18.0.2. Он не знает про veth, bridge, iptables и dockerd.

## 3.2 Обзор сетевых драйверов

Docker «из коробки» предоставляет несколько драйверов. На практике 95% задач закрывают первые четыре:

| Драйвер | Для чего | Область | Когда использовать |
|---|---|---|---|
| **`bridge`** (дефолт) | Контейнеры на **одном** хосте общаются друг с другом | Локальный хост Создаёт veth-пару, цепляет один конец к bridge, добавляет iptables NAT | Обычные приложения, compose-сервисы на одной машине |
| **`host`** | Убрать изоляцию, использовать сеть хоста напрямую | Локальный хост Те же интерфейсы, что у хоста (lo, eth0 хоста) — namespace не создаётся Ничего не делает — контейнер просто переиспользует сетевой namespace хоста | Высокая производительность, инструменты, которые не любят NAT |
| **`none`** | Полная изоляция от сети | Локальный хост Не создаёт veth, не даёт IP | Безопасные batch-задачи, тесты без сети |
| **`overlay`** | Контейнеры на **разных** хостах общаются как в одной сети | Мульти-хост (Swarm) eth0 с IP из overlay-подсети (например, 10.0.0.5), resolv.conf с 127.0.0.11 Создаёт veth + VXLAN-туннель до других хостов Swarm | Swarm-сервисы, распределённые приложения |
| **`macvlan`** | Контейнер выглядит как физическое устройство с MAC | Локальная L2-сеть | Легаси-приложения, которым нужен «настоящий» MAC |
| **`ipvlan`** | Похож на macvlan, но без уникального MAC | Локальная L2/L3-сеть | Ограничение на количество MAC в сети |

**Мнемоника:**

- **bridge** — «своя песочница на одном хосте»;
- **host** — «я и есть хост»;
- **none** — «меня нет в сети»;
- **overlay** — «мост между хостами»;
- **macvlan/ipvlan** — «я физическое устройство в вашей LAN».

## 3.3 `bridge`: дефолтная сеть и почему она не одна

### 3.3.1 Два bridge: `docker0` и пользовательские

При установке Docker создаёт **дефолтный** bridge-интерфейс `docker0` (обычно `172.17.0.0/16`). Все контейнеры, запущенные **без** `--network`, попадают в него.

Но **дефолтный bridge — это историческое наследие**, и у него есть ограничения:

- **Нет встроенного DNS** по именам контейнеров (только через `--link`, который устарел).
- Все контейнеры видят друг друга **по IP**, но не по имени.
- Изоляция слабая: любой контейнер в `docker0` может достучаться до любого другого.

**Пользовательский bridge** (user-defined bridge) решает эти проблемы:

```bash
docker network create my-net
docker run -d --name app --network my-net myapp:latest
docker run -d --name db  --network my-net postgres:16
```

Теперь `app` может обращаться к `db` **по имени** (`ping db` работает), потому что Docker включает **встроенный DNS** для пользовательских сетей.

### 3.3.2 Как это устроено под капотом

```
Хост
├── docker0 (172.17.0.1)          ← дефолтный bridge
│   └── veth... ↔ контейнер A (172.17.0.2)
│
└── br-<hash> (172.18.0.1)        ← пользовательский bridge "my-net"
    ├── veth... ↔ контейнер B (172.18.0.2)  ← app
    └── veth... ↔ контейнер C (172.18.0.3)  ← db
```

Каждый контейнер получает **veth-пару**: один конец — в контейнере (`eth0`), другой — подключён к bridge на хосте. Ядро Linux **forward’ит** пакеты между veth-интерфейсами, а `iptables` делает NAT для выхода наружу.



### 3.3.3 Создание с параметрами

```bash
docker network create \
  --driver bridge \
  --subnet 172.20.0.0/16 \
  --gateway 172.20.0.1 \
  --ip-range 172.20.5.0/24 \
  my-custom-net
```

- **`--subnet`** — диапазон адресов;
- **`--gateway`** — шлюз (по умолчанию первый адрес в подсети);
- **`--ip-range`** — из какого поддиапазона выдавать IP контейнерам.

**Важно:** пользовательские bridge-сети **изолированы друг от друга**. Контейнер в `my-net` не увидит контейнер в `other-net`, если их не соединить явно.

## 3.4 `host`: без изоляции, с последствиями

### 3.4.1 Что происходит

`--network host` **убирает** сетевой namespace. Контейнер использует **стек хоста напрямую**: тот же `eth0`, тот же `127.0.0.1`, те же порты.

```bash
docker run --rm --network host nginx
```

Теперь nginx слушает **порт 80 на хосте** напрямую. Нет NAT, нет `-p`, нет veth.

### 3.4.2 Последствия, о которых нужно знать

1. **`-p` игнорируется.** В host-режиме у контейнера нет своего IP, поэтому **проброс портов не работает**. Флаги `-p`, `--publish`, `-P` просто игнорируются (или вызывают ошибку в строгом режиме).

2. **Конфликты портов реальны.** Если nginx в контейнере слушает 80, а на хосте уже есть сервис на 80 — контейнер **не запустится**. Порт должен быть **свободен на хосте**.

3. **Производительность лучше.** Нет NAT, нет veth, нет `iptables`-forward. Для высоконагруженных сетевых приложений (прокси, балансировщики) это может дать заметный выигрыш.

4. **Безопасность хуже.** Контейнер видит **все** интерфейсы хоста, включая `localhost`-сервисы. Если приложение скомпрометировано — оно имеет доступ к большему, чем в bridge-режиме.

### 3.4.3 Когда использовать

- Высокопроизводительные сетевые инструменты (например, `netshoot` для дебага).
- Приложения, которые **должны** видеть реальные интерфейсы хоста.
- **Не** для обычных веб-сервисов — для них bridge + `-p` безопаснее и предсказуемее.

## 3.5 `none`: полная изоляция

`--network none` создаёт контейнер **только с loopback** (`lo`). Никаких `eth0`, никакого выхода наружу.

```bash
docker run --rm --network none alpine sh -c 'ip addr'
# 1: lo: <LOOPBACK,UP> ...
# (никаких других интерфейсов)
```

**Зачем:**

- **Безопасные batch-задачи**, которым сеть не нужна (обработка файлов, криптография).
- **Тесты**, которые должны доказать, что приложение не делает сетевых вызовов.
- **Изоляция** подозрительного кода.

**Важно:** `none` **недоступен** для Swarm-сервисов.

## 3.6 `overlay`: сеть между хостами

### 3.6.1 Что это

`overlay` создаёт **распределённую сеть** поверх физических сетей нескольких Docker-хостов. Контейнеры на **разных машинах** видят друг друга так, будто они в одной локальной сети.

```
Хост A (192.168.1.10)              Хост B (192.168.1.11)
┌─────────────────────┐            ┌─────────────────────┐
│  overlay: my-net    │            │  overlay: my-net    │
│  ┌───────────────┐  │            │  ┌───────────────┐  │
│  │ container A   │  │            │  │ container B   │  │
│  │ 10.0.0.2      │──┼────────────┼──│ 10.0.0.3      │  │
│  └───────────────┘  │  VXLAN     │  └───────────────┘  │
│                     │  (UDP 4789)│                     │
└─────────────────────┘            └─────────────────────┘
```

### 3.6.2 Требования

1. **Swarm mode обязателен.** Даже для standalone-контейнеров на разных хостах нужно, чтобы хосты были частью одного Swarm.
2. **Порты между хостами:**
   - **2377/tcp** — control plane Swarm;
   - **4789/udp** — data plane (VXLAN);
   - **7946/tcp+udp** — gossip между нодами.

### 3.6.3 Создание

```bash
# На manager-ноде
docker network create -d overlay --attachable my-overlay
```

- **`--attachable`** позволяет подключать **standalone-контейнеры** (не только Swarm-сервисы).
- Без `--attachable` сеть доступна **только** Swarm-сервисам.

### 3.6.4 Шифрование

```bash
docker network create \
  --driver overlay \
  --opt encrypted \
  --attachable \
  my-secure-overlay
```

`--opt encrypted` включает **IPsec** на уровне VXLAN. **Цена:** заметное падение производительности — тестируй перед продом.

**Важно:** шифрование **не поддерживается** для Windows-контейнеров.

## 3.7 DNS: как контейнеры находят друг друга по имени

### 3.7.1 Встроенный DNS `127.0.0.11`

Docker запускает **встроенный DNS-сервер** по адресу `127.0.0.11` **внутри каждого контейнера**, подключённого к **пользовательской** сети.

```bash
docker run --rm --network my-net alpine cat /etc/resolv.conf
# nameserver 127.0.0.11
# options ndots:0
```

**Ключевое ограничение:** встроенный DNS работает **только** в **пользовательских** сетях (user-defined). В **дефолтном** `docker0` его нет — там резолвинг по именам не работает (только по IP или через устаревший `--link`).

### 3.7.2 Как это работает

1. Контейнер делает DNS-запрос (например, `ping db`).
2. Запрос идёт на `127.0.0.11` (встроенный DNS Docker).
3. Docker проверяет: есть ли в этой сети контейнер с именем (или сетевым алиасом) `db`.
4. Если да — возвращает его IP **в этой сети**.
5. Если нет — **форвардит** запрос на **upstream DNS** (хоста или указанный в `--dns`).

### 3.7.3 Имена и алиасы

- **Имя контейнера** (`--name`) — автоматически резолвится.
- **Сетевой алиас** (`--network-alias`) — дополнительное имя:

```bash
docker run -d --name app --network my-net --network-alias api myapp
# Теперь и "app", и "api" резолвятся в один и тот же IP
```

- **`--link`** — устаревший механизм, **не использовать** в новых проектах.

### 3.7.4 Кастомный DNS

Если нужен свой DNS-сервер (корпоративный, Pi-hole и т.д.):

```bash
docker run --dns 192.168.1.250 --dns 1.1.1.1 myapp
```

Или глобально в `/etc/docker/daemon.json`:

```json
{
  "dns": ["192.168.1.250", "1.1.1.1"]
}
```

**Важно:** `127.0.0.11` остаётся первым в `/etc/resolv.conf`, но если Docker не может разрешить имя локально — он **форвардит** запрос на указанные upstream-серверы.

## 3.8 Port publishing: как выставить сервис наружу

### 3.8.1 Зачем

В bridge-режиме контейнер имеет **внутренний** IP (`172.x.x.x`), недоступный с хоста и из внешней сети. Чтобы достучаться до сервиса, нужно **опубликовать порт** — Docker создаст `iptables`-правило, которое перенаправит трафик с порта хоста на порт контейнера.

### 3.8.2 Синтаксис `-p`

```bash
docker run -p 8080:80 nginx
```

- **`8080`** — порт **на хосте**;
- **`80`** — порт **в контейнере**.

Формула: `-p <host_port>:<container_port>`.

### 3.8.3 Варианты

| Запись | Что делает |
|---|---|
| `-p 8080:80` | Порт 8080 на **всех** интерфейсах хоста → порт 80 контейнера |
| `-p 127.0.0.1:8080:80` | Только на `localhost` хоста (недоступно извне) |
| `-p 8080:80/udp` | UDP-порт (по умолчанию TCP) |
| `-p 8080:80 -p 8443:443` | Несколько портов |
| `-P` | Опубликовать **все** `EXPOSE`-порты на случайные порты хоста |

### 3.8.4 `EXPOSE` в Dockerfile vs `-p` при запуске

```dockerfile
EXPOSE 80
```

`EXPOSE` **не публикует** порт. Это **метаданные** («этот образ слушает 80»), которые:
- видны в `docker inspect`;
- используются флагом `-P` (publish all);
- **не** создают `iptables`-правил.

**Публикация** происходит **только** при `docker run -p` (или `-P`).

### 3.8.5 Как это работает под капотом

Docker добавляет в `iptables` правила в цепочке `DOCKER` (nat table):

```
-A DOCKER -p tcp --dport 8080 -j DNAT --to-destination 172.17.0.2:80
```

Пакет, пришедший на хост-порт 8080, **DNAT**-ится на IP контейнера и порт 80. Обратный трафик проходит через **SNAT** (masquerade), чтобы контейнер видел «клиента» как шлюз, а не как внешний IP.

### 3.8.6 Host-режим: `-p` **не работает**

В `--network host` у контейнера **нет своего IP**, поэтому проброс портов **невозможен**. `-p` игнорируется (или вызывает ошибку в строгом режиме). Контейнер просто слушает порт **напрямую на хосте** — и если порт занят, будет конфликт.

## 3.9 `network inspect`: что смотреть и как фильтровать

### 3.9.1 Базовый вызов

```bash
docker network inspect my-net
```

По умолчанию выводит **большой JSON** со всеми полями. Ключевые секции:

| Поле | Что содержит |
|---|---|
| **`Driver`** | Драйвер (`bridge`, `overlay`, ...) |
| **`IPAM.Config`** | Подсеть, шлюз, диапазон IP |
| **`Containers`** | Контейнеры в сети: ID, имя, IPv4, MAC |
| **`Options`** | Дополнительные опции драйвера |
| **`Scope`** | `local` или `swarm` |

### 3.9.2 Полезные `--format`-шаблоны

**Подсеть и шлюз:**

```bash
docker network inspect my-net --format '{{range .IPAM.Config}}subnet={{.Subnet}} gateway={{.Gateway}}{{end}}'
```

**Список контейнеров с IP:**

```bash
docker network inspect my-net --format '{{range $id, $c := .Containers}}{{$c.Name}} → {{$c.IPv4Address}}{{"\n"}}{{end}}'
```

**Только имена контейнеров:**

```bash
docker network inspect my-net --format '{{range .Containers}}{{.Name}} {{end}}'
```

### 3.9.3 Для overlay: `--verbose`

Для Swarm-overlay сетей `--verbose` показывает **VIP** (virtual IP) сервисов и порты:

```bash
docker network inspect --verbose my-overlay
```

## 3.10 Типичные ошибки и подводные камни

### 3.10.1 DNS не работает в дефолтном bridge

```
$ docker run --rm alpine ping another-container
ping: bad address 'another-container'
```

**Причина:** встроенный DNS (`127.0.0.11`) активен **только** в пользовательских сетях. В `docker0` резолвинга по именам нет.

**Решение:** создай пользовательскую сеть и подключи оба контейнера к ней.

### 3.10.2 `-p` в host-режиме игнорируется

```
$ docker run --network host -p 8080:80 nginx
# (порт 80 занят на хосте напрямую, -p ни на что не влияет)
```

**Причина:** в host-режиме у контейнера нет своего IP, проброс портов невозможен.

**Решение:** либо убрать `-p` (и слушать порт напрямую), либо использовать bridge.

### 3.10.3 Overlay не работает без Swarm

```
$ docker network create -d overlay my-net
Error response from daemon: This node is not a swarm manager.
```

**Причина:** overlay требует **Swarm mode**, даже для standalone-контейнеров.

**Решение:** `docker swarm init` на manager-ноде, `docker swarm join` на worker’ах.

### 3.10.4 Конфликт портов в host-режиме

```
$ docker run --network host nginx
# Error: bind: address already in use
```

**Причина:** порт 80 уже занят на хосте (например, другим nginx).

**Решение:** остановить конфликтующий сервис или использовать bridge + `-p` на другой порт.

### 3.10.5 Забыли `--attachable` для overlay

```
$ docker run --network my-overlay alpine
# Error: network my-overlay not found
```

**Причина:** overlay-сеть без `--attachable` доступна **только** Swarm-сервисам.

**Решение:** пересоздать сеть с `--attachable`.

## 3.11 Шпаргалка: что использовать в каком случае

| Задача | Инструмент |
|---|---|
| Контейнеры на **одном хосте** общаются по именам | **user-defined bridge** + `--network` |
| Выставить сервис **наружу** | **bridge** + `-p host:container` |
| Максимальная **производительность** сети | **`--network host`** |
| Полная **изоляция** от сети | **`--network none`** |
| Контейнеры на **разных хостах** | **overlay** + Swarm + `--attachable` |
| Контейнер должен выглядеть как **физическое устройство** в LAN | **macvlan** |
| Нужен **DNS** по именам контейнеров | **user-defined** сеть (bridge или overlay) |
| Отладить сеть | `docker network inspect`, `--format`, `--verbose` |

## Вопросы контрольные

**1. Почему в дефолтном bridge (`docker0`) не работает `ping` по имени контейнера, а в пользовательском — работает?**

Ответ: встроенный DNS Docker (`127.0.0.11`) активен **только** в пользовательских сетях. В `docker0` его нет: контейнеры видят друг друга **только по IP**. Пользовательская сеть при подключении контейнера настраивает `/etc/resolv.conf` на `127.0.0.11`, и Docker резолвит имена контейнеров и сетевые алиасы **в пределах этой сети**.

**2. Ты запускаешь `docker run --network host -p 8080:80 nginx`. Порт 8080 на хосте свободен, но nginx не отвечает на 8080. Почему?**

Ответ: в `--network host` у контейнера **нет собственного IP-адреса**, он использует сетевой стек хоста напрямую. Поэтому **проброс портов не работает** — флаг `-p` игнорируется. Nginx слушает **порт 80 на хосте** (а не 8080), и если порт 80 свободен — он будет доступен на 80, а не на 8080. Чтобы опубликовать 8080, нужен **bridge-режим** (без `--network host`) + `-p 8080:80`.

**3. В чём разница между `EXPOSE 80` в Dockerfile и `-p 8080:80` при `docker run`?**

Ответ: `EXPOSE` — это **метаданные**. Он не создаёт `iptables`-правил и не публикует порт. Он лишь сообщает, что образ **слушает** порт 80, и используется флагом `-P` (publish all) для автоматической публикации на случайные порты хоста. **Публикация** происходит **только** при `docker run -p` (или `-P`), который создаёт DNAT-правило в `iptables`. Без `-p` (или `-P`) сервис внутри контейнера **недоступен** с хоста, даже если в Dockerfile есть `EXPOSE`.

**4. Overlay-сеть создана с `--opt encrypted`. Какие порты должны быть открыты между хостами и что это даёт?**

Ответ: для overlay нужны **2377/tcp** (control plane Swarm), **4789/udp** (data plane VXLAN) и **7946/tcp+udp** (gossip между нодами). Флаг `--opt encrypted` включает **IPsec** на уровне VXLAN: трафик между контейнерами на разных хостах **шифруется**. Это даёт защиту от прослушивания в сети, но **снижает производительность** (IPsec — дорогая операция). Для Windows-контейнеров шифрование **не поддерживается**.

**5. `docker network inspect my-net` показывает контейнер с IP `172.20.0.5`, но `ping 172.20.0.5` с хоста не работает. Почему?**

Ответ: контейнер в bridge-сети имеет **внутренний IP** (`172.20.0.5`), который **не маршрутизируется** с хоста напрямую. Хост **не является** частью этой bridge-сети: он подключён к bridge-интерфейсу (`br-<hash>`) с адресом `172.20.0.1`, но `172.20.0.5` — это адрес **внутри** bridge-сегмента. Чтобы достучаться до контейнера, нужно либо **опубликовать порт** (`-p`), либо **войти в сеть** контейнера через `docker exec`, либо использовать **host-режим**. Прямой `ping` с хоста в контейнер по внутреннему IP **не работает** без дополнительной маршрутизации.

**6. Ты подключил контейнер к двум bridge-сетям: `frontend` и `backend`. Какой шлюз по умолчанию он выберет?**

Ответ: по умолчанию Docker выбирает шлюз сети с **наивысшим приоритетом** (`gw-priority`). Если приоритеты не заданы, поведение может быть непредсказуемым (зависит от порядка подключения). Чтобы **гарантировать** выбор, задай приоритет явно: `docker run --network name=frontend,gw-priority=1 --network backend ...` — тогда шлюз `frontend` станет default gateway. Это важно, когда одна сеть имеет выход наружу, а другая — только внутренняя.
