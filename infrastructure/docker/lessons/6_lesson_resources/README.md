# Docker — Урок 6. Ресурсы: `--memory`, `--cpus`, `--pids-limit`, cgroup v2, OOM

## 6.1 Модель угроз: контейнер без лимитов — это «шумный сосед» с правом на убийство

По умолчанию Docker **не накладывает никаких ограничений на ресурсы**: контейнер может использовать столько памяти, CPU и процессов, сколько позволит ядро хоста. Это создаёт три класса проблем:

1. **Шумный сосед (noisy neighbour).** Один контейнер выедает всю память или CPU, и страдают все остальные контейнеры и сам хост.
2. **Fork bomb.** Процесс внутри контейнера может породить бесконечное число потомков, исчерпав PID-ы на хосте и сделав систему неработоспособной.
3. **OOM на уровне хоста.** Если у контейнера нет лимита памяти, а хост исчерпал RAM, ядро запускает **OOM killer** и может убить **любой** процесс, включая `dockerd` или критичные системные службы. Docker пытается защитить демон, повышая его OOM-приоритет, но контейнеры такой защиты не имеют.

**Принцип:** лимиты ресурсов — это не «оптимизация производительности», а **границы поражения** (blast radius). Они гарантируют, что сбой или атака в одном контейнере не утащат за собой хост и соседей.

## 6.2 Память: `--memory` и смежные флаги

### 6.2.1 Жёсткий лимит: `--memory` (`-m`)

```bash
docker run --memory 512m alpine
```

Задаёт **жёсткий потолок** памяти, которую может использовать контейнер. Если контейнер пытается превысить лимит, ядро запускает **cgroup OOM killer** и убивает процесс (обычно PID 1) сигналом `SIGKILL`. Минимальное допустимое значение — `6m`.

### 6.2.2 Swap: `--memory-swap`

`--memory-swap` работает **только вместе** с `--memory` и задаёт **общий** объём памяти + swap.

| `--memory` | `--memory-swap` | Что получает контейнер |
|---|---|---|
| `300m` | `1g` | 300 МБ RAM + 700 МБ swap |
| `300m` | не задан | 300 МБ RAM + до 300 МБ swap (итого до 600 МБ) |
| `300m` | `300m` | 300 МБ RAM, **swap запрещён** |
| `300m` | `-1` | 300 МБ RAM + неограниченный swap (опасно) |

> ⚠️ `free` внутри контейнера показывает swap **хоста**, а не доступный контейнеру. Не полагайтесь на него для проверки лимита.

### 6.2.3 Мягкий лимит: `--memory-reservation`

Задаёт **soft limit**, который активируется только при нехватке памяти или конкуренции на хосте. Должен быть **меньше** `--memory`. Полезен, чтобы контейнер в спокойное время мог использовать больше памяти, но при давлении сжимался до резерва.

### 6.2.4 `--oom-kill-disable`: почему это почти всегда плохо

```bash
docker run --memory 256m --oom-kill-disable alpine   # НЕ ДЕЛАЙТЕ ТАК
```

Флаг **отключает** OOM killer для контейнера. Docker позволяет использовать его **только если задан `--memory`**, иначе при исчерпании памяти хоста ядро начнёт убивать **системные** процессы. Даже с `--memory` это опасно: контейнер просто «зависнет» в неаллоцируемом состоянии, вместо того чтобы быть перезапущенным. В продакшене `--oom-kill-disable` **не используется**.

## 6.3 CPU: `--cpus`, `--cpu-shares`, `--cpuset-cpus`

Docker использует **CFS (Completely Fair Scheduler)** ядра Linux. Флаги ниже меняют настройки cgroup контейнера на хосте.

### 6.3.1 `--cpus`: жёсткий потолок

```bash
docker run --cpus="1.5" alpine
```

Контейнер гарантированно получит **не более 1.5 ядра CPU**. Эквивалент ручной установки `--cpu-period=100000` и `--cpu-quota=150000`. Это самый удобный и распространённый способ ограничить CPU.

### 6.3.2 `--cpu-shares`: мягкий вес

```bash
docker run --cpu-shares=512 alpine
```

Задаёт **относительный вес** (по умолчанию `1024`). Работает **только при конкуренции за CPU**: если ядра свободны, контейнер может использовать сколько угодно. `--cpu-shares` не гарантирует и не резервирует конкретную долю CPU. Это **не** лимит, а приоритет.

### 6.3.3 `--cpuset-cpus`: привязка к ядрам

```bash
docker run --cpuset-cpus="0-3" alpine      # только CPU 0,1,2,3
docker run --cpuset-cpus="1,3" alpine      # только CPU 1 и 3
```

Ограничивает, на **каких физических ядрах** может выполняться контейнер. Полезно для latency-sensitive нагрузок и NUMA-оптимизации.

### 6.3.4 `--cpu-quota` / `--cpu-period`: ручная настройка

`--cpus` — это удобная обёртка. Внутри `--cpus="1.5"` превращается в `--cpu-period=100000` и `--cpu-quota=150000` (150 мс квоты на каждые 100 мс периода). В большинстве случаев используйте `--cpus`; ручные флаги нужны только для тонкой настройки или совместимости.

## 6.4 PIDs: `--pids-limit` и защита от fork bomb

```bash
docker run --pids-limit 100 alpine
```

Ограничивает **максимальное количество процессов и потоков** (tasks) в cgroup контейнера. В cgroup v2 это записывается в `pids.max`. Значение `-1` или `0` означает «без лимита».

**Зачем:** без `--pids-limit` процесс-вымогатель или сбойное приложение может выполнить fork bomb и исчерпать PID-ы на хосте. С лимитом `pids.max` новые `fork()`/`clone()` начнут возвращать ошибку (`EAGAIN`), но хост останется жив.

**Сколько ставить:** для типичных веб-приложений ориентир — **100–500 PIDs**, но точное значение зависит от рантайма (JVM и Go создают много потоков). Начинайте с большего значения и снижайте, наблюдая за `pids.current`.

## 6.5 Cgroup v2: как Docker реализует лимиты

Cgroup (control group) — это механизм ядра, который группирует процессы и накладывает на группу ограничения. Docker создаёт для каждого контейнера отдельную cgroup и записывает туда значения флагов.

### 6.5.1 Cgroup v1 vs v2: где смотреть файлы

| Ресурс | Cgroup v1 (старое) | Cgroup v2 (актуальное) |
|---|---|---|
| Память (жёсткий лимит) | `/sys/fs/cgroup/memory/memory.limit_in_bytes` | `/sys/fs/cgroup/memory.max` |
| Память (текущее потребление) | `memory.usage_in_bytes` | `memory.current` |
| Память (пиковое потребление) | `memory.max_usage_in_bytes` | `memory.peak` |
| CPU (квота/период) | `cpu.cfs_quota_us` + `cpu.cfs_period_us` | `cpu.max` (одна строка: `QUOTA PERIOD`) |
| PIDs | `pids.max` | `pids.max` |
| OOM-события | `memory.oom_control` | `memory.events` |

На современных дистрибутивах (Ubuntu 22.04+, Debian 12+, Fedora, а также AWS Bottlerocket/AL2023) по умолчанию используется **cgroup v2**. Docker поддерживает cgroup v2 начиная с версии 20.10; требуется ядро **4.15+** (рекомендуется **5.2+**).

### 6.5.2 Как проверить лимиты изнутри контейнера

```bash
# cgroup v2
cat /sys/fs/cgroup/memory.max      # 536870912  (512 MiB)
cat /sys/fs/cgroup/cpu.max         # 50000 100000  (0.5 CPU)
cat /sys/fs/cgroup/pids.max        # 512
```

Если в файле стоит `max` — лимит не задан.

### 6.5.3 Cgroup v2 и rootless-контейнеры

Cgroup v2 особенно важен для **rootless-режима**: без него ограничения CPU, памяти и PIDs в rootless-контейнерах либо не работают, либо работают частично. Если вы используете rootless Docker, убедитесь, что хост загружен с cgroup v2.

## 6.6 OOM: как распознать и что делать

### 6.6.1 Код выхода 137 — это ещё не приговор

`137 = 128 + 9`, то есть процесс получил **SIGKILL**. Но кто его послал — большой вопрос:

| Симптом | Что произошло | Что проверить |
|---|---|---|
| `ExitCode: 137`, `OOMKilled: true` | Cgroup-лимит памяти превышен, ядро убило PID 1 | `docker inspect` → `State.OOMKilled` |
| `ExitCode: 137`, `OOMKilled: false`, в `dmesg` есть OOM | Ядро убило **дочерний** процесс внутри контейнера, PID 1 выжил | `memory.events` → счётчик `oom_kill` |
| `ExitCode: 137`, `OOMKilled: false`, в `dmesg` **нет** OOM | Внешний SIGKILL: `docker kill`, `docker stop` с таймаутом, оркестратор, CI | Логи демона, настройки `--stop-timeout` |

### 6.6.2 Быстрая диагностика

```bash
# 1. Флаг OOMKilled и код выхода
docker inspect --format '{{.State.OOMKilled}} {{.State.ExitCode}}' <container>

# 2. Текущее потребление против лимита
docker stats --no-stream --format "table {{.Name}}\t{{.MemUsage}}\t{{.MemPerc}}" <container>

# 3. Счётчик OOM-убийств в cgroup (v2)
cat /sys/fs/cgroup/system.slice/docker-<id>.scope/memory.events
# oom 5
# oom_kill 5

# 4. Логи ядра
dmesg | grep -i "oom\|killed process" | tail -20
```

Путь к cgroup на systemd-хостах с v2 обычно `/sys/fs/cgroup/system.slice/docker-<id>.scope/`; на v1 — `/sys/fs/cgroup/memory/docker/<id>/`.

### 6.6.3 Почему JVM/Node/Python «не видят» лимит

Классическая ловушка: контейнеру дали `--memory 4g`, внутри JVM выставили `-Xmx3g`, и кажется, что есть 1 ГБ запаса. Но JVM потребляет не только heap: метапространство, direct memory, стеки потоков, CodeCache, GC-структуры. **RSS легко превышает `--memory`**, и контейнер получает OOM kill, хотя «куча» далека от предела.

Старые версии JVM (до 8u191) вообще читали **память хоста**, а не cgroup-лимит. Современные рантаймы умеют определять cgroup, но **direct memory** всё равно нужно ограничивать явно (`-XX:MaxDirectMemorySize`), а лимит контейнера ставить с запасом **×1.3** от суммы heap + non-heap.

**Правило для любого рантайма:** проверяйте, что приложение **осознаёт** cgroup-лимит, и не ставьте внутренний лимит равным внешнему — оставляйте запас на накладные расходы.

### 6.6.4 Как чинить

- **Если это cgroup OOM:** поднимите `--memory` (с запасом) или найдите утечку. Если потребление растёт монотонно до kill — это утечка, а не «мало памяти».
- **Если это дочерний OOM:** лимит всё равно мал для всей группы процессов; поднимите его. В идеале — перейдите к **однопроцессной модели** на контейнер, чтобы Docker видел OOM через `OOMKilled: true`.
- **Если это внешний SIGKILL:** проверьте `--stop-timeout` (по умолчанию 10 с) и обработку `SIGTERM` в приложении. Увеличьте таймаут или научите приложение корректно завершаться.

## 6.7 Как выставлять лимиты: практический алгоритм

1. **Запустите без лимитов** и прогоните **реалистичную** нагрузку, включая тяжёлые операции (бэкап, реиндекс, bulk import).
2. **Снимите пик.** `docker stats --no-stream` показывает только мгновенное значение; пик памяти в cgroup v2 — `memory.peak`.
3. **Поставьте лимит выше пика с запасом.** Распространённая отправная точка — **пик + 50%**.
4. **Смотрите на сигналы:** `OOMKilled`, рост `memory.events/oom_kill`, `cpu.stat` с throttling. Если лимит слишком тесный — **поднимите, а не убирайте**.

Пример для production-контейнера:

```bash
docker run -d \
  --memory 512m \
  --memory-swap 512m \
  --cpus "0.50" \
  --pids-limit 200 \
  --restart unless-stopped \
  myapp:1.0
```

## 6.8 Сравнительная таблица: «что когда использовать»

| Задача | Флаг | Уровень |
|---|---|---|
| Жёсткий потолок памяти | `--memory` | **Обязательно** для прода |
| Запретить swap | `--memory-swap` = `--memory` | Рекомендуется |
| Мягкий резерв памяти | `--memory-reservation` | При конкуренции за RAM |
| Жёсткий лимит CPU | `--cpus` | **Обязательно** для прода |
| Приоритет CPU (вес) | `--cpu-shares` | При нескольких контейнерах |
| Привязка к ядрам | `--cpuset-cpus` | Latency-sensitive нагрузки |
| Защита от fork bomb | `--pids-limit` | **Обязательно** для недоверенного кода |
| Диагностика OOM | `docker inspect`, `memory.events`, `dmesg` | При инциденте |
| Отключение OOM killer | `--oom-kill-disable` | **Не использовать** |

**Мнемоника «слои защиты ресурсов»:**

```
--memory (не может съесть RAM хоста)
  ↓
--cpus (не может занять все ядра)
  ↓
--pids-limit (не может исчерпать PID-ы)
  ↓
cgroup v2 (ядро реально применяет лимиты)
  ↓
мониторинг OOM (ты узнаёшь о проблеме раньше пользователей)
```

## Вопросы контрольные

**1. В чём разница между `--memory` и `--memory-reservation`?**

Ответ: `--memory` — **жёсткий** лимит: превышение ведёт к OOM kill. `--memory-reservation` — **мягкий** лимит: активируется только при нехватке памяти или конкуренции на хосте; в спокойное время контейнер может использовать больше. `--memory-reservation` должен быть меньше `--memory`.

**2. Почему `--oom-kill-disable` опасен даже с `--memory`?**

Ответ: Он отключает механизм, который освобождает память при переполнении. Контейнер не будет убит, но и не сможет получить память — он «зависнет» в неработоспособном состоянии. Без `--memory` флаг вообще может привести к тому, что ядро начнёт убивать системные процессы хоста, включая `dockerd`.

**3. Контейнер завершился с кодом 137, но `OOMKilled: false`. Что это может быть?**

Ответ: Это **не** cgroup OOM kill. Варианты: (а) ядро убило **дочерний** процесс внутри контейнера — проверьте `memory.events` → `oom_kill`; (б) внешний SIGKILL — `docker kill`, `docker stop` с истёкшим таймаутом, оркестратор или CI отправили сигнал.

**4. Чем `--cpus` отличается от `--cpu-shares`?**

Ответ: `--cpus` — **жёсткий** потолок: контейнер никогда не превысит заданное число ядер. `--cpu-shares` — **относительный вес** при конкуренции: если CPU свободен, контейнер может использовать сколько угодно; вес влияет только когда несколько контейнеров борются за ядра.

**5. Зачем нужен `--pids-limit`, если есть `ulimit`?**

Ответ: `ulimit -u` (RLIMIT_NPROC) ограничивает число процессов **на пользователя**, что грубо и не учитывает cgroup-иерархию. `--pids-limit` ограничивает число задач **именно в cgroup контейнера** (файл `pids.max`), что точнее и не зависит от того, под каким UID работает процесс.

**6. Где в cgroup v2 посмотреть, был ли OOM kill?**

Ответ: В файле `memory.events` внутри cgroup контейнера. Счётчики `oom` (сколько раз OOM срабатывал) и `oom_kill` (сколько процессов реально убито). Путь на systemd-хосте: `/sys/fs/cgroup/system.slice/docker-<id>.scope/memory.events`.
