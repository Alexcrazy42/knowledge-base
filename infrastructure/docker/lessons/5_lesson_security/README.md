# Docker — Урок 5. Безопасность: capabilities, seccomp, --read-only, USER, rootless, --security-opt


## 5.1 Модель угроз: контейнер — это не «песочница» по умолчанию

Контейнер **изолирует** процесс (namespaces, cgroups, overlay2), но **не** делает его **безопасным** автоматически. Основные риски:

1. **Процесс внутри — root.** По умолчанию `docker run alpine` запускает **root (UID 0)** внутри контейнера. Если приложение скомпрометировано — атакующий **уже root** внутри контейнера (с ограничениями, но root).
2. **14 capabilities по умолчанию.** Docker **не** даёт «полный root» — он **отбрасывает** опасные capabilities. Но **оставляет** 14 «безопасных» (например, `NET_RAW`, `CHOWN`, `SETUID`, `SETGID`), которых **достаточно** для многих атак.
3. **Seccomp фильтрует ~44 syscall**, но **не** все. Некоторые опасные (например, `ptrace` в старых версиях) могут быть **разрешены** в зависимости от профиля.
4. **Writable rootfs.** Если rootfs **writable** — атакующий может **записать** payload (скрипт, бинарник) и **выполнить** его.
5. **Daemon работает от root.** Если **демон** скомпрометирован — атакующий получает **root на хосте**. Это **самый** опасный сценарий.

**Принцип наименьших привилегий (least privilege):** дать контейнеру **ровно столько** прав, **сколько нужно**, и **ни капли больше**.

## 5.2 Capabilities: «root, разрезанный на кусочки»

### 5.2.1 Что это

В Linux **root** — это не «одно право», а **набор** из ~40 **capabilities** (возможностей). Каждая capability даёт **конкретное** право:

| Capability | Что даёт | Опасность |
|---|---|---|
| `CAP_CHOWN` | Менять владельца файла | Средняя |
| `CAP_NET_RAW` | Создавать raw-сокеты (ping, tcpdump) | **Высокая** — можно спуфить пакеты |
| `CAP_SYS_ADMIN` | **«Новый root»** — монтирование, namespaces, многое | **Критическая** — почти всё |
| `CAP_SYS_PTRACE` | Трассировать процессы (ptrace) | **Высокая** — можно читать память других процессов |
| `CAP_NET_BIND_SERVICE` | Биндить порты < 1024 | Низкая |

**Docker по умолчанию** даёт контейнеру **14** capabilities (allowlist), а **остальные** — **отбрасывает**. Это **лучше**, чем «полный root», но **всё равно** слишком много для **большинства** приложений.

### 5.2.2 `--cap-drop` и `--cap-add`

```bash
# Отбросить ВСЕ capabilities
docker run --cap-drop=ALL alpine id

# Отбросить все, добавить только нужную
docker run --cap-drop=ALL --cap-add=NET_BIND_SERVICE nginx
```

**Правило:** **сначала** `--cap-drop=ALL`, **потом** `--cap-add` **только** то, что **действительно** нужно.

**Пример:** для nginx, который слушает порт 80 (privileged port), нужна `NET_BIND_SERVICE`:

```bash
docker run --cap-drop=ALL --cap-add=NET_BIND_SERVICE -p 80:80 nginx
```

**Пример:** для `ping` (raw-сокеты) нужна `NET_RAW`:

```bash
docker run --cap-drop=ALL --cap-add=NET_RAW alpine ping 8.8.8.8
```

**Важно:** `--cap-add=ALL` **опасен** — это почти полный root. Избегайте.

### 5.2.3 Связь с seccomp

**Seccomp** и **capabilities** работают **вместе**. Seccomp **фильтрует** syscall (на **уровне ядра**), capabilities **ограничивают** права **внутри** разрешённых syscall.

**Пример:** `mount` — это syscall. Seccomp **может** его **разрешить** (если он в allowlist), но **capability** `SYS_ADMIN` **всё равно** нужна, чтобы `mount` **сработал**. **Два** уровня защиты.

## 5.3 Seccomp: «фильтр syscall»

### 5.3.1 Что это

**Seccomp** (secure computing mode) — это **механизм ядра Linux**, который **фильтрует** системные вызовы (syscall). Контейнер **может** делать **только** те syscall, которые **разрешены** профилем.

**Docker по умолчанию** применяет **default seccomp profile**, который:
- **разрешает** ~300 syscall (allowlist);
- **блокирует** ~44 **опасных** syscall (например, `ptrace`, `mount`, `bpf`, `keyctl`).

**Default профиль — allowlist:** всё, что **не** разрешено — **запрещено** (`SCMP_ACT_ERRNO`, возвращает `Permission denied`).

### 5.3.2 Когда нужен кастомный профиль

**Default профиль** — **разумный** компромисс между безопасностью и совместимостью. **Но** некоторым приложениям **нужны** syscall, которых **нет** в allowlist (например, `clone3` для новых версий Node.js, или `perf_event_open` для профилирования). В **этом** случае — **кастомный** профиль.

**Создание кастомного профиля:**

```json
{
  "defaultAction": "SCMP_ACT_ERRNO",
  "syscalls": [
    {
      "names": ["clone3", "perf_event_open"],
      "action": "SCMP_ACT_ALLOW"
    }
  ]
}
```

**Применение:**

```bash
docker run --security-opt seccomp=/path/to/profile.json myapp
```

**Важно:** Docker CLI **читает** профиль **на клиенте** и **отправляет** содержимое **демону** — профиль **должен** быть **доступен** на **хосте клиента**, если клиент и демон **разные**.

### 5.3.3 «Выключить seccomp» — плохая идея

```bash
docker run --security-opt seccomp=unconfined myapp
```

**Это** **отключает** seccomp **полностью**. Контейнер **получает** **все** syscall. **Никогда** не делайте это в проде — **только** для отладки.

## 5.4 `--read-only`: «заморозить» rootfs

### 5.4.1 Что это

`--read-only` монтирует **root filesystem** контейнера **read-only**. Процесс **может** **читать** файлы, но **не** **писать** в них.

```bash
docker run --read-only alpine sh -c 'echo test > /tmp/f.txt'
# sh: can't create /tmp/f.txt: Read-only file system
```

**Зачем:** если атакующий **скомпрометировал** приложение, он **не может**:
- записать **payload** (скрипт, бинарник) в rootfs;
- изменить **бинарники** или **конфиги**;
- создать **backdoor** в файловой системе.

### 5.4.2 Как жить с `--read-only`

**Приложение** обычно **нуждается** в **записи** куда-то (логи, кэш, temp). Решение:

1. **`--tmpfs`** для **временных** файлов (в памяти):
```bash
docker run --read-only --tmpfs /tmp --tmpfs /run alpine myapp
```

2. **Named volume** или **bind mount** для **persistent** данных:
```bash
docker run --read-only -v mydata:/var/lib/app alpine myapp
```

**Всё**, что **не** в tmpfs и **не** в volume — **read-only**.

### 5.4.3 Ограничения

- **Не работает** для приложений, которые **пишут** в **собственные** директории (например, некоторые Java-приложения пишут в `$CATALINA_HOME`).
- **Некоторые** пакетные менеджеры (apt, yum) **требуют** записи в `/var/lib/dpkg` или `/var/lib/rpm`.
- **Отладка** сложнее — **нельзя** установить `strace` или `tcpdump` в **работающий** контейнер.

**Правило:** `--read-only` — **цель**, к которой **стоит** стремиться, но **не** всегда **достижима** без **адаптации** приложения.

## 5.5 `USER`: «не root внутри контейнера»

### 5.5.1 Проблема

По умолчанию `docker run` запускает процесс **от root (UID 0)**. Если приложение **скомпрометировано** — атакующий **уже root** внутри контейнера. Если **volume** смонтирован с хоста — атакующий **может** **изменить** файлы на хосте (в **пределах** прав root).

### 5.5.2 Решение: `USER` в Dockerfile

```dockerfile
FROM alpine
RUN addgroup -S appgroup && adduser -S appuser -G appgroup
USER appuser
CMD ["myapp"]
```

**Всё** после `USER appuser` **выполняется** от **непривилегированного** пользователя.

**Важно:** `USER` **должен** быть **до** `CMD`/`ENTRYPOINT`, и **файлы**, которые **нужны** приложению, **должны** быть **доступны** `appuser` (через `chown` или `COPY --chown`).

### 5.5.3 `--user` в `docker run`

```bash
docker run --user 1000:1000 alpine id
# uid=1000 gid=1000
```

**Переопределяет** `USER` из Dockerfile. **Полезно** для **отладки** или **совместимости** с **хостом**.

### 5.5.4 Non-root и capabilities

**Non-root** **не** значит «без capabilities». **Non-root** пользователь **может** иметь **capabilities**, если они **даны** (через `--cap-add`). **Но** `--cap-drop=ALL` **вместе** с `USER` — **сильнее**, чем **просто** `USER`.

**Правило:** **`USER` + `--cap-drop=ALL` + `--read-only`** — **базовый** набор для **любого** production-контейнера.

## 5.6 Rootless mode: «демон без root»

### 5.6.1 Проблема

В **классическом** Docker **демон** (`dockerd`) работает **от root**. Если **демон** скомпрометирован — атакующий **получает** **root на хосте**. Это **самый** опасный сценарий.

### 5.6.2 Что такое rootless

**Rootless mode** позволяет **демону** и **контейнерам** работать **от непривилегированного** пользователя. Даже **установка** Docker **не** требует root (при **выполнении** prerequisites).

**Как это работает:** Docker **использует** **user namespace** — контейнер **думает**, что он root (UID 0), но **на хосте** это **непривилегированный** UID (например, 1000). Если **контейнер** скомпрометирован — атакующий **получает** **только** права **пользователя 1000**, а **не** root.

### 5.6.3 Установка

```bash
# Prerequisites: newuidmap, newgidmap, /etc/subuid, /etc/subgid
dockerd-rootless-setuptool.sh install
```

**Требуется:** 65 536 subordinate UID/GID в `/etc/subuid` и `/etc/subgid`.

### 5.6.4 Ограничения

- **Нельзя** использовать **privileged ports** (< 1024) **без** `CAP_NET_BIND_SERVICE` на **rootlesskit**.
- **Overlay2** может быть **недоступен** (используется **fuse-overlayfs**).
- **Некоторые** функции (например, `--net=host`) **работают** **иначе**.

**Rootless** — **рекомендуемый** режим для **dev-машин** и **CI**, но **не** всегда **подходит** для **прода** (из-за **ограничений** производительности и совместимости).

## 5.7 `--security-opt`: «швейцарский нож» безопасности

`--security-opt` — это **общий** флаг для **разных** механизмов безопасности. **Основные** применения:

| Опция | Что делает |
|---|---|
| `--security-opt seccomp=profile.json` | **Кастомный** seccomp-профиль |
| `--security-opt seccomp=unconfined` | **Отключить** seccomp (**опасно!**) |
| `--security-opt apparmor=profile` | **AppArmor** профиль (на **Ubuntu/Debian**) |
| `--security-opt no-new-privileges=true` | **Запретить** процессу **получать** новые привилегии (через `setuid`/`setgid`) |
| `--security-opt label=level:s0:c100,c200` | **SELinux** метка (на **RHEL/CentOS**) |

**`no-new-privileges`** — **простой** и **мощный** флаг. Он **гарантирует**, что **даже** если процесс **имеет** `setuid`-бинарник, он **не** получит **новых** прав.

```bash
docker run --security-opt no-new-privileges:true --cap-drop=ALL alpine myapp
```

## 5.8 Сравнительная таблица: «что когда использовать»

| Задача | Инструмент | Уровень |
|---|---|---|
| **Базовый** non-root | `USER` в Dockerfile | **Обязательно** |
| **Ограничить** capabilities | `--cap-drop=ALL --cap-add=...` | **Обязательно** для прода |
| **Ограничить** syscall | **seccomp** (default профиль) | **Уже** включён |
| **Кастомный** seccomp | `--security-opt seccomp=...` | Для **специфичных** приложений |
| **Заморозить** rootfs | `--read-only` | **Сильно** рекомендуется |
| **Запретить** повышение привилегий | `--security-opt no-new-privileges=true` | **Рекомендуется** |
| **Демон без root** | **Rootless mode** | Для dev/CI; **осторожно** в проде |
| **AppArmor/SELinux** | `--security-opt apparmor=...` / `label=...` | На **соответствующих** хостах |

**Мнемоника «слои безопасности» (defense in depth):**

```
USER (не root)
  ↓
--cap-drop=ALL (минимум capabilities)
  ↓
seccomp (минимум syscall)
  ↓
--read-only (нельзя писать)
  ↓
no-new-privileges (нельзя повысить права)
  ↓
Rootless (даже демон не root)
```

**Каждый** слой **убирает** **часть** возможностей атакующего. **Если** один слой **пробит** — **следующий** **останавливает**.

## Вопросы контрольные

**1. Почему `docker run --cap-add=ALL` — плохая идея?**

Ответ: `--cap-add=ALL` даёт контейнеру **все** Linux capabilities, включая `CAP_SYS_ADMIN` («новый root»), `CAP_SYS_PTRACE` (чтение памяти других процессов), `CAP_NET_RAW` (спуфинг пакетов). Это **почти** полный root. Если приложение скомпрометировано — атакующий получает **огромные** возможности внутри контейнера, и **риск** выхода на хост **резко** возрастает. Правильно: `--cap-drop=ALL` + `--cap-add` **только** необходимого.

**2. В чём разница между `--cap-drop=ALL` и `--security-opt seccomp=unconfined`?**

Ответ: `--cap-drop=ALL` **убирает** capabilities (права **внутри** разрешённых syscall). `--security-opt seccomp=unconfined` **отключает** seccomp — контейнер **может** делать **все** syscall (даже те, что **были** заблокированы). Это **противоположные** действия: первое **усиливает** безопасность, второе — **ослабляет**. `seccomp=unconfined` **никогда** не использовать в проде — **только** для отладки.

**3. Ты добавил `USER appuser` в Dockerfile, но приложение падает с `Permission denied` при записи в `/app/data`. Почему? Что исправить?**

Ответ: `USER appuser` меняет пользователя **только** для **процесса**. Файлы в `/app/data` **унаследованы** из образа и **принадлежат** `root` (потому что `COPY`/`RUN` **до** `USER` выполнялись от root). `appuser` **не** имеет прав на запись. Исправить: **до** `USER appuser` выполнить `chown -R appuser:appgroup /app/data`, или использовать `COPY --chown=appuser:appgroup` для **копирования** файлов с **правильным** владельцем.

**4. В чём разница между `--read-only` и `--tmpfs /tmp`?**

Ответ: `--read-only` делает **весь** rootfs **read-only**. Процесс **не может** писать **никуда**, кроме **явно** смонтированных **writable** мест. `--tmpfs /tmp` монтирует **только** `/tmp` как **writable** (в памяти). Это **не** делает rootfs read-only — **остальные** части rootfs **остаются** writable. **Правильно** комбинировать: `--read-only --tmpfs /tmp` — rootfs read-only, **но** `/tmp` writable (для **временных** файлов).

**5. Rootless mode: почему это **безопаснее** обычного Docker?**

Ответ: В **обычном** Docker **демон** (`dockerd`) работает **от root**. Если **демон** скомпрометирован — атакующий **получает** **root на хосте**. В **rootless** **демон** и **контейнеры** работают **от непривилегированного** пользователя (через **user namespace**). Даже если **контейнер** скомпрометирован — атакующий **получает** **только** права **пользователя** (например, UID 1000), а **не** root. **Риск** для **хоста** **резко** снижается.

**6. `--security-opt no-new-privileges=true`: что именно он запрещает?**

Ответ: Он **запрещает** процессу **получать** **новые** привилегии через `execve` — например, через **`setuid`/`setgid`-бинарники** (как `sudo` или `ping` с `setuid`-битом). Если процесс **запущен** от **непривилегированного** пользователя, он **не** может **повысить** права, **даже** если **выполнит** `setuid`-бинарник. Это **простой** и **мощный** способ **предотвратить** **повышение** привилегий **внутри** контейнера.
